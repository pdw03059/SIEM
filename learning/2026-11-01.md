# 1. 오늘 만든 기능과 MAZKION 전체에서의 위치

이번 자료에서 **코드로 확인할 수 있는 기능**은 두 가지입니다.

1. 오류 목록 하나를 바탕으로 오류 코드 열거형과 오류 정보 표를 함께 만드는 X-매크로 패턴
2. 쿼리 명령어 이름을 처리 함수에 연결하고, 이름으로 찾아 실행하는 등록 표(registration table) 패턴

둘 다 `docs/examples/registry/registry_demo.c`에 있는 교육용 예제입니다. `head`와 `count`는 SIEM 데이터를 처리하는 실제 쿼리라기보다, 등록 표가 함수를 찾아 호출하는 방식을 보여 주는 간단한 함수입니다. `head`는 결과에 10을 쓰고, `count`는 입력 문자열 길이를 결과로 씁니다 (`docs/examples/registry/registry_demo.c:63-80`).

**MAZKION 전체 구현에서 어디에 연결되는지는 제공된 코드만으로 확인할 수 없습니다.** PR 본문은 `ARCHITECTURE.md`, `CODING_RULES.md` 등 문서 작업을 설명하지만, 이 문서들의 실제 내용이나 서버 코드·쿼리 엔진 코드는 제공하지 않았습니다. 따라서 이번 예제를 MAZKION 서버의 실제 명령 처리 경로라고 단정해서는 안 됩니다.

# 2. 왜 필요한가 — SIEM 현장 문제와의 연결

SIEM에는 여러 종류의 쿼리나 기능이 생깁니다. 명령어마다 처리 코드를 길게 `if`/`else`로 이어 붙이는 대신, **명령어 이름과 함수 주소를 한 표에 등록하고 그 표를 검색하는 방식**을 쓰면 등록 정보가 한곳에 모입니다. 이 예제에서는 이름, 함수 포인터, 도움말이 한 항목에 들어갑니다 (`docs/examples/registry/registry_demo.c:82-95`). 도움말을 같은 표에서 출력하는 흐름도 보여 줍니다 (`docs/examples/registry/registry_demo.c:123-125`).

오류도 현장에서 단순한 숫자만 보이면 운영자가 원인을 파악하기 어렵습니다. 이 예제의 오류 정보 표는 오류 코드뿐 아니라 심각도, 요약, 영향, 원인 후보, 조치를 함께 담는 형태입니다 (`docs/examples/registry/registry_demo.c:26-42`). 오류를 출력할 때도 이 정보를 정해진 형식으로 보여 줍니다 (`docs/examples/registry/registry_demo.c:54-61`).

SIEM 관점에서 이 두 패턴이 유용할 수 있는 이유는 다음과 같습니다.

- **오류 대응의 일관성:** 모듈마다 오류 문구와 조치 형식이 제각각 되는 문제를 줄일 수 있습니다.
- **확장 지점의 가시성:** 등록된 기능을 한 표에서 확인할 수 있습니다.
- **자동화 가능성:** 등록된 이름과 도움말을 이용해 목록을 출력하는 기반을 만들 수 있습니다.

다만 이 예제에는 로그 이벤트, 네트워크 수신, 저장, 검색, 권한 검증 기능이 없습니다. 따라서 SIEM의 전체 문제를 해결하는 코드는 아니며, 그 안에서 사용할 수 있는 **작은 설계 패턴을 시연하는 코드**로 이해해야 합니다.

# 3. 운영체제·네트워크 관점의 동작

## 프로세스와 실행 파일

Makefile의 `test` 대상은 `registry_demo`를 만든 뒤 실행합니다 (`docs/examples/registry/Makefile:17-18`). 실행 시 프로그램은 `main`에서 시작해 오류 목록과 명령어 목록을 출력하고, 세 가지 검사를 수행한 다음 종료 코드를 돌려줍니다 (`docs/examples/registry/registry_demo.c:117-133`).

운영체제는 프로그램을 실행할 때 프로세스를 만들고, 프로그램의 코드와 전역 데이터 등을 메모리에 올립니다. 다만 이 예제는 **프로세스 생성 함수를 직접 호출하지 않습니다.** 운영체제 내부에서 어떤 구체적 시스템 호출이 사용되는지는 제공된 코드만으로 확인할 수 없습니다.

## 표준 출력과 오류 출력

코드는 `printf`로 정상 진행 정보와 결과를, `fprintf(stderr, ...)`로 검사 실패 메시지를 출력합니다 (`docs/examples/registry/registry_demo.c:12-13`, `docs/examples/registry/registry_demo.c:113`). C 프로그램 관점에서는 표준 출력(`stdout`)과 표준 오류(`stderr`)라는 스트림을 쓰는 것입니다. 운영체제에는 보통 이 스트림과 연결된 파일 디스크립터가 있지만, 코드에는 파일 디스크립터를 직접 다루는 호출이 없습니다.

## 네트워크·소켓·스레드·버퍼

소켓, 네트워크 통신, 스레드, 프로세스 간 통신, 명시적 입출력 버퍼 관리 코드는 제공된 파일에 없습니다. 따라서 이 예제로는 서버의 연결 관리나 이벤트 전송 동작을 설명할 수 없습니다. 현재 코드의 데이터 흐름은 **프로그램 안에서 등록 표를 검색하고 함수를 호출하는 것**에 한정됩니다 (`docs/examples/registry/registry_demo.c:97-105`).

# 4. 사용한 C 기술

## 열거형과 X-매크로

열거형은 오류 이름들을 정수 값으로 다루기 위한 타입입니다. 같은 `mz_errors.def` 목록을 서로 다른 매크로 정의와 함께 두 번 포함해, 한 번은 열거형 항목으로, 한 번은 구조체 배열 초기값으로 바꿉니다 (`docs/examples/registry/registry_demo.c:18-24`, `docs/examples/registry/registry_demo.c:36-42`). 이 기법을 X-매크로라고 부릅니다.

실제 오류 이름이나 목록의 내용은 제공된 `mz_errors.def`가 없으므로 확인할 수 없습니다. 코드에는 그 파일이 포함되어 있다는 사실과 `MZ_ERR_QRY_UNKNOWN_CMD` 같은 오류 이름만 보입니다 (`docs/examples/registry/registry_demo.c:21`, `docs/examples/registry/registry_demo.c:104`).

## 구조체와 읽기 전용 표

`mz_err_info_t`와 `mz_cmd_entry_t`는 각 항목의 여러 값을 묶는 구조체입니다 (`docs/examples/registry/registry_demo.c:26-34`, `docs/examples/registry/registry_demo.c:82-87`). `static const` 배열은 이 파일 안에서만 쓰이고 프로그램 실행 중 바뀌지 않도록 선언되어 있습니다 (`docs/examples/registry/registry_demo.c:39-41`, `docs/examples/registry/registry_demo.c:90-93`).

배열 자체는 항목을 담고 있지만, 각 항목의 문자열은 `const char *` 포인터입니다. `mz_err_info`는 구조체 전체를 복사하지 않고 표 안의 항목을 가리키는 주소를 반환합니다 (`docs/examples/registry/registry_demo.c:47-52`).

## 함수 포인터

`mz_cmd_fn`은 특정 모양의 함수를 가리키는 포인터 타입입니다. 함수는 문자열 인자와 결과를 쓸 `int *`를 받고, `mz_err_t` 오류 코드를 돌려줍니다 (`docs/examples/registry/registry_demo.c:65-66`). 등록 표에 함수 주소를 넣고, 검색 결과로 그 함수를 호출합니다 (`docs/examples/registry/registry_demo.c:90-93`, `docs/examples/registry/registry_demo.c:100-104`).

## 포인터와 출력 매개변수

`out`은 정수의 주소를 전달받습니다. 처리 함수는 `*out`에 값을 기록하고, 호출자는 그 값을 읽을 수 있습니다 (`docs/examples/registry/registry_demo.c:69-80`, `docs/examples/registry/registry_demo.c:110-112`). 이 방식은 함수의 반환값을 오류 코드로 쓰면서 결과값도 별도로 전달할 때 사용됩니다.

하지만 호출자가 `out == NULL`을 전달하면 `*out`을 쓰는 부분에서 잘못된 메모리 접근이 발생할 수 있습니다. 현재 예제의 호출은 유효한 주소를 넘기지만, 함수 자체에는 NULL 검사 코드가 없습니다 (`docs/examples/registry/registry_demo.c:69-80`, `docs/examples/registry/registry_demo.c:110-112`).

## 배열 크기와 오류 검사

`sizeof 배열 / sizeof 배열[0]`로 배열 항목 수를 계산합니다 (`docs/examples/registry/registry_demo.c:44-45`, `docs/examples/registry/registry_demo.c:94-95`). 명령어 수를 별도로 손으로 갱신하지 않아도 되는 장점이 있습니다.

`mz_err_info`는 입력 오류 값이 표 범위를 벗어나면 `NULL`을 반환하고, 그렇지 않으면 표의 주소를 반환합니다 (`docs/examples/registry/registry_demo.c:47-52`). 이는 배열 범위를 벗어난 접근을 막는 검사입니다. 다만 뒤에서 이 함수의 반환값을 검사 없이 역참조하는 호출 경로도 있으므로, 모든 사용이 안전하다고 일반화해서는 안 됩니다 (`docs/examples/registry/registry_demo.c:110-113`).

## 메모리 할당

이 코드에는 `malloc`이나 `free` 같은 동적 메모리 할당·해제 호출이 없습니다. 등록 표와 오류 표는 정적으로 정의되어 있고, `check`의 지역 변수 `out`은 함수 호출 동안 사용하는 정수입니다 (`docs/examples/registry/registry_demo.c:39-41`, `docs/examples/registry/registry_demo.c:90-93`, `docs/examples/registry/registry_demo.c:108-114`).

- **5줄:** 보여 줄 내용을 나열하기 시작합니다.
- **6줄:** X-매크로로 오류 열거형과 오류 정보 표를 만든다는 목적을 설명합니다.
- **7줄:** 명령어 이름과 처리 함수의 대응 표를 만든다는 목적을 설명합니다.
- **8줄:** 빈 설명 주석 줄입니다.
- **9줄:** 빌드·시험 방법과 참고 문서를 안내합니다.

### 16–25줄: 오류 열거형 생성

- **16줄:** 오류 코드 구간의 제목 주석입니다.
- **17줄:** 구간을 나누는 빈 줄입니다.
- **18줄:** 뒤에서 `MZ_ERR`를 열거형 항목 생성용으로 정의할 것임을 설명합니다.
- **19줄:** 각 `MZ_ERR(...)` 행을 첫 번째 인자 `id`만 남기는 형태로 바꿉니다. 다른 인자들은 이 매크로 확장 결과에 포함되지 않습니다.
- **20줄:** 익명 `enum`을 시작합니다. 열거형 항목들은 정수 상수로 쓰입니다.
- **21줄:** `mz_errors.def`를 현재 매크로 정의 상태에서 포함합니다. 이 파일의 각 `MZ_ERR` 행이 열거형 항목으로 확장됩니다. 단, 목록 파일의 실제 내용은 제공되지 않았습니다.
- **22줄:** 오류 항목 개수를 나타내는 끝 항목을 추가합니다. 실제 값이 정확히 목록 개수와 일치하려면 앞선 항목의 구성과 순서가 기대한 형태여야 합니다.
- **23줄:** 이 열거형에 `mz_err_t`라는 타입 이름을 붙입니다.
- **24줄:** `MZ_ERR` 매크로를 지워 다음 용도에서 다시 정의할 수 있게 합니다.
- **25줄:** 빈 줄입니다.

### 26–46줄: 오류 정보 구조체와 표

- **26줄:** 오류 항목의 사람이 읽을 정보를 설명하는 주석입니다.
- **27줄:** 오류 정보 구조체 정의를 시작합니다.
- **28줄:** 오류 코드 문자열을 가리키는 포인터 필드입니다.
- **29줄:** 심각도 문자열 필드입니다.
- **30줄:** 요약 문자열 필드입니다.
- **31줄:** 영향 설명 문자열 필드입니다.
- **32줄:** 원인 후보 문자열 필드입니다.
- **33줄:** 조치 설명 문자열 필드입니다.
- **34줄:** 구조체에 `mz_err_info_t`라는 타입 이름을 붙입니다.
- **35줄:** 빈 줄입니다.
- **36줄:** 같은 오류 목록을 이번에는 구조체 초기값으로 바꾸겠다는 설명입니다.
- **37줄:** `MZ_ERR` 매크로를 다시 정의합니다. 이번에는 각 행에서 구조체 항목을 생성합니다.
- **38줄:** 지정 초기화(`[id] = ...`)를 사용해 `id`에 해당하는 배열 위치에 오류 정보를 넣습니다.
- **39줄:** 오류 정보 배열을 파일 내부에서만 볼 수 있고 수정되지 않도록 정의합니다. 배열 데이터에 문자열 포인터가 들어갑니다.
- **40줄:** `mz_errors.def`를 다시 포함해 배열 항목들을 생성합니다. 첫 번째 포함과 다르게 이번에는 구조체 초기값으로 확장됩니다.
- **41줄:** 배열 초기화와 선언을 닫습니다.
- **42줄:** 재정의한 `MZ_ERR` 매크로를 지웁니다.
- **43줄:** 빈 줄입니다.
- **44줄:** 배열 크기와 오류 코드 개수가 같은지 컴파일 시 확인한다는 주석입니다.
- **45줄:** 배열의 항목 수와 `MZ_ERR__COUNT`가 다르면 컴파일을 실패시킵니다. 단, 이것이 모든 오류 ID가 빠짐없이 연속인지까지 독립적으로 증명하는 것은 아닙니다.
- **46줄:** 빈 줄입니다.

### 47–61줄: 오류 정보 조회와 출력

# 6. 나머지 변경 파일의 흐름 — 함수 호출 순서와 데이터 이동만 요약

그 밖의 변경 코드 패치는 제공되지 않았습니다. PR 본문에는 `ARCHITECTURE.md`, `CODING_RULES.md`, `AUTOMATION_BACKLOG.md` 등의 변경 요약이 있지만, 해당 파일의 실제 내용은 제공되지 않았으므로 내부 흐름이나 구현을 해설할 수 없습니다.

제공된 C 예제의 호출 흐름은 다음과 같습니다.

1. `main`이 오류 코드 수와 오류 정보를 출력합니다.
2. `main`이 명령어 이름과 도움말을 등록 표에서 읽어 출력합니다.
3. `check`가 `mz_cmd_dispatch`를 호출합니다.
4. `mz_cmd_dispatch`가 등록 표를 순회해 이름을 비교합니다.
5. 이름을 찾으면 함수 포인터로 처리 함수를 호출하고, 못 찾으면 알 수 없는 명령어 오류 코드를 반환합니다.
6. `check`는 반환 코드를 출력하고 기대값과 비교합니다.
7. `main`은 검사 실패 수에 따라 종료 코드를 정합니다 (`docs/examples/registry/registry_demo.c:117-132`).

# 7. 메모리 변화와 장애 시나리오 — 가득 차면, 연결이 끊기면, 프로세스가 죽으면, 악성·비정상 입력이 들어오면

## 메모리는 어떻게 변하나

이 예제에서 오류 표와 명령어 표는 정적으로 정의되어 있습니다. 실행 중 명령어를 등록하거나 표를 늘리는 동적 할당 코드는 없습니다 (`docs/examples/registry/registry_demo.c:39-41`, `docs/examples/registry/registry_demo.c:90-93`). `check`가 호출될 때는 결과 정수와 반환 오류 코드 같은 지역 변수가 사용됩니다 (`docs/examples/registry/registry_demo.c:108-112`).

등록 항목이 많아지면 명령어 검색은 표를 처음부터 비교하는 방식이므로 비교 횟수가 늘어납니다 (`docs/examples/registry/registry_demo.c:100-104`). 표가 메모리에서 가득 차는 상황을 처리하는 동적 용량 관리 코드는 없습니다. 표 크기는 소스 코드에 등록한 항목에 따라 정해집니다.

## 명령어가 등록되지 않았을 때

`sort`처럼 표에 없는 이름은 순회를 마친 뒤 `MZ_ERR_QRY_UNKNOWN_CMD`를 반환합니다 (`docs/examples/registry/registry_demo.c:100-105`). 이 예제의 검사는 이 반환값을 기대값과 비교합니다 (`docs/examples/registry/registry_demo.c:130-130`).

## 잘못된 포인터나 비정상 문자열이 들어올 때

- `name == NULL`이면 `strcmp`에 유효하지 않은 포인터가 전달될 수 있습니다. 디스패처에는 NULL 검사가 없습니다 (`docs/examples/registry/registry_demo.c:98-104`).
- `arg == NULL`이면 `cmd_count`의 `strlen`이 유효하지 않은 포인터를 읽을 수 있습니다. `cmd_head`는 인자를 사용하지 않지만, 디스패처 차원의 검증은 없습니다 (`docs/examples/registry/registry_demo.c:69-79`).
- `out == NULL`이면 처리 함수가 `*out`에 결과를 기록할 때 잘못된 메모리 접근이 발생할 수 있습니다 (`docs/examples/registry/registry_demo.c:69-79`).
- 반환된 오류 값이 표 범위를 벗어나면 `mz_err_info`는 `NULL`을 돌려줍니다 (`docs/examples/registry/registry_demo.c:47-52`). `mz_err_print`는 이 경우를 처리하지만 (`docs/examples/registry/registry_demo.c:57-60`), `check`는 반환 포인터를 확인하지 않고 접근합니다 (`docs/examples/registry/registry_demo.c:110-113`).

실제 서버에서 신뢰할 수 없는 쿼리 입력을 받는지는 이 예제로 확인할 수 없습니다. 다만 등록 표를 실제 요청 처리에 연결한다면 이름 길이, 널 종료 여부, 권한, 함수 인자의 유효성을 어느 계층에서 검증할지 별도로 설계해야 합니다.

## 연결이 끊기거나 디스크가 가득 차면

이 코드에는 네트워크 연결이나 디스크 쓰기가 없습니다. 따라서 연결 끊김, 스풀 공간 부족, 디스크 가득 참, 데이터 전달 실패의 실제 처리 방식은 **제공된 코드로는 확인 불가**입니다.

## 프로세스가 죽으면

프로세스가 비정상 종료되면 해당 실행의 출력이 중간까지만 보일 수 있습니다. 이 예제에는 오류 표나 결과를 디스크에 저장하는 코드가 없으므로 재시작 후 상태를 복구하는 동작도 없습니다. 반대로 말하면, 이 예제는 실행 중 보존해야 하는 SIEM 이벤트 상태를 다루지 않습니다.

# 8. 상용 SIEM과의 비교와 개선점 — 같은 문제를 일반적인 상용 제품은 어떻게 다루는지(공개 자료·일반적으로 알려진 수준만, 추정은 "추정"으로 표시, 특정 제품 내부 구현을 아는 것처럼 쓰지 말 것)와 MAZKION이 더 낫게 할 점

일반적으로 상용 SIEM은 여러 입력·검색·관리 기능을 함께 제공하고, 오류와 기능의 노출 방식을 제품 인터페이스나 문서로 일관되게 구성합니다. 다만 제품마다 설계가 다르며, 특정 제품이 내부에서 이 예제와 같은 X-매크로나 등록 표를 쓴다고 말할 근거는 없습니다.

이 코드에서 확인되는 방식은 작고 명시적입니다.

- 오류 정의 목록 하나를 두 형태로 재사용합니다 (`docs/examples/registry/registry_demo.c:18-24`, `docs/examples/registry/registry_demo.c:36-42`).
- 명령어 이름, 처리 함수, 도움말을 한 배열에 둡니다 (`docs/examples/registry/registry_demo.c:82-95`).
- 표를 직접 순회해 이름을 찾습니다 (`docs/examples/registry/registry_demo.c:97-105`).

MAZKION이 이 패턴을 제품 수준으로 확장할 때 검토할 개선점은 다음과 같습니다.

1. **입력 검증:** 이름·인자·결과 포인터가 유효한지 검사하고, 잘못된 입력을 안전한 오류 코드로 바꿉니다. 현재 예제에는 해당 검사가 없습니다 (`docs/examples/registry/registry_demo.c:98-104`).
2. **검사 강화:** 성공 여부만 비교하지 말고, 결과값이 기대한 값인지도 검사합니다. 현재 `check`는 반환 오류 코드만 비교합니다 (`docs/examples/registry/registry_demo.c:108-114`).
3. **오류 정보 접근의 일관성:** `mz_err_info`가 `NULL`을 반환할 수 있음을 모든 호출자가 고려하도록 합니다. 현재 출력 함수는 검사하지만 시험 함수는 검사하지 않습니다 (`docs/examples/registry/registry_demo.c:47-60`, `docs/examples/registry/registry_demo.c:110-113`).
4. **규모에 맞는 검색:** 명령어 수가 커지면 선형 검색이 충분한지 측정한 뒤 자료구조를 선택합니다. 이 예제의 검색은 선형 순회입니다 (`docs/examples/registry/registry_demo.c:100-104`).
5. **운영 관측성:** 실제 서버에 적용할 때는 오류 발생 빈도, 입력 출처, 처리 지연, 재시도 여부 등을 운영자가 확인할 수 있게 설계할 수 있습니다. 이 예제에는 그런 기록 기능이 없습니다.

PR 본문은 아키텍처 문서의 저장·전달, 백프레셔, 이중화, 성능 등의 내용을 요약하지만, 실제 문서와 서버 구현이 제공되지 않았습니다. 따라서 위 항목들이 현재 MAZKION에 구현되어 있는지, 상용 제품보다 나은지에 대한 평가는 **제공된 코드로는 확인 불가**입니다. PR 본문의 요약만으로 실제 구현 상태를 단정하지 않는 것이 중요합니다.

# 9. 직접 해 보기 — 빌드·실행·수정 명령과 예상 결과 (제공된 자료에 있는 Makefile·명령만, 없으면 확인 불가로 표시)

자료에 있는 실행 명령은 다음과 같습니다.

```sh
make -C docs/examples/registry test
```

이 명령은 Makefile의 `test` 대상을 실행합니다. 실행 파일이 필요하면 C11 옵션으로 컴파일하고, 이어서 `registry_demo`를 실행합니다 (`docs/examples/registry/Makefile:14-18`). PR 본문은 이 시험에서 3/3 통과했다고 보고합니다. 실제 출력은 `mz_errors.def`에 담긴 오류 목록 내용에 따라 달라질 수 있으며, 그 파일은 제공되지 않았습니다.

sanitizer를 이용한 시험 명령은 다음과 같습니다.

```sh
make -C docs/examples/registry test-san
```

이 명령은 AddressSanitizer와 UndefinedBehaviorSanitizer 옵션으로 별도 실행 파일을 만들고 실행합니다 (`docs/examples/registry/Makefile:8-9`, `docs/examples/registry/Makefile:20-22`). PR 본문에는 이 시험도 통과했다고 적혀 있지만, 여기서는 실제 실행 결과를 재현한 것이 아닙니다.

빌드 결과를 지우는 명령은 Makefile에 다음과 같이 정의되어 있습니다.

```sh
make -C docs/examples/registry clean
```

이는 일반 실행 파일과 sanitizer 실행 파일을 제거합니다 (`docs/examples/registry/Makefile:24-27`).

코드를 수정하는 실습으로는 `cmd_count`가 입력 문자열 길이를 반환하는 현재 동작을 확인한 뒤, 검사 함수가 기대 결과값도 비교하도록 바꿔 볼 수 있습니다. 다만 수정 후 예상되는 출력 형식이나 수정 절차를 위한 별도 스크립트는 제공된 자료에 없습니다. 실습 전후의 정확한 빌드 결과는 실제 환경에서 확인해야 합니다.

# 11. 다음에 공부할 것

1. **C의 포인터와 문자열 계약:** NULL 포인터, 널 종료 문자열, `strlen`·`strcmp`의 전제 조건을 익힙니다.

3. **컴파일 전처리:** X-매크로가 실제 C 코드로 어떻게 확장되는지 전처리 결과를 확인하는 방법을 배웁니다. 단, 그 실습에 쓸 추가 명령은 제공된 자료에 없습니다.

# 정답 — 10장 복습 문제의 정답과 해설

1. **첫 번째 포함은 오류 열거형을, 두 번째 포함은 오류 정보 표를 만듭니다.** 첫 정의에서는 각 행을 오류 ID만 남기도록 하고, 두 번째 정의에서는 같은 행을 구조체 초기값으로 바꿉니다 (`docs/examples/registry/registry_demo.c:18-24`, `docs/examples/registry/registry_demo.c:36-42`). 목록을 한곳에서 관리하므로 두 표현의 목록이 따로 작성될 때 생길 수 있는 불일치를 줄일 수 있습니다. 단, 목록 파일 자체가 제공되지 않아 실제 항목은 확인할 수 없습니다.

2. **등록된 이름을 찾지 못하면 `MZ_ERR_QRY_UNKNOWN_CMD`를 반환합니다.** 검색은 첫 항목부터 순서대로 각 이름을 비교하므로 항목이 늘어날수록 최악의 경우 더 많은 비교가 필요합니다 (`docs/examples/registry/registry_demo.c:100-105`). 이 예제에서는 빠른 검색 구조가 아니라 단순하고 이해하기 쉬운 표 순회를 사용합니다.

3. **`mz_err_info(got)`가 `NULL`을 반환해도 `check`가 결과를 검사하지 않고 `->code`에 접근할 수 있습니다.** 범위를 벗어난 오류 값이면 조회 함수가 `NULL`을 반환하도록 되어 있습니다 (`docs/examples/registry/registry_demo.c:47-52`). 반면 `mz_err_print`는 NULL을 확인합니다 (`docs/examples/registry/registry_demo.c:57-60`). 또 `check`는 반환 오류 코드가 기대값과 같은지만 확인하며, `out`에 저장된 결과값이 기대한 값인지 검사하지 않습니다 (`docs/examples/registry/registry_demo.c:108-114`).
