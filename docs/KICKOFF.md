# SIEM 프로젝트 착수 문서 (새 대화 시작용)


## 1. 프로젝트 개요
- **목표**: 상용 SIEM 제품군의 공개된 기능을 모두 갖추고, 각 기능을 더 좋게 만든 SIEM을 처음부터 개발
- **발주자**: 저장소 소유자 (SIEM 운영 경험 보유)
- **언어**: 에이전트·전달 서버·분석 엔진·웹 API 모두 **C (C11)**. 웹 UI는 TypeScript + React. 메타데이터는 SQLite에서 시작해 이후 PostgreSQL로 전환
- **학습 목적**: C 코드는 **한 줄마다 한국어 주석**을 달고, TypeScript는 블록 단위로 상세 주석

## 2. 개발 원칙 (클린룸)
- 상용 제품을 디컴파일한 코드와 내부 구현은 **참고하지 않는다**. 비공개 자료(셸 가이드 초안 등)도 쓰지 않는다.
- 기능 목록은 **공개 자료**에서 정리한다: 상용 SIEM들의 공개 문서, 릴리스 노트, 공식 블로그.
- 개선 방향은 **발주자의 현장 경험**에서 정한다(아래 4장).
- 상용 제품과의 비교는 설치한 제품을 밖에서 측정하는 **블랙박스 벤치마크**로 한다.

## 3. 시스템 구성
```
[에이전트] → [전달 서버] → [분석 서버] ← [웹 UI / 대시보드]
 파일·Syslog·      디스크 버퍼·     저장·인덱스·쿼리 엔진
 Windows 이벤트    재전송·부하분산   실시간·배치 시나리오, 이상징후 탐지
                                    티켓·소명, 이중화(액티브·스탠바이)
```

## 4. 개선 목표 (현장 사례 기반)
| 기존 운영 환경에서 겪은 문제 | 새 설계 목표 |
|---|---|
| 테이블 하나의 쓰기가 막히면 전달 채널 전체가 정지(금융사 A, 공유 잠금 누적) | 테이블별 독립 쓰기 큐·워커, 장애가 다른 테이블로 번지지 않게 격리 |
| ring 적체가 통계에 0으로 나타나고 잠금 원인을 알기 어려움 | 전달 지연량, 잠금 보유자, 대기 시간을 실시간 지표와 셸로 노출 |
| 힙·DM 튜닝 필수, Full GC로 정지(사례 B·C) | C 엔진으로 GC를 없애고 캐시 상한을 자동 관리 |
| 센트리 세션 단절 후 pending close로 재연결 불가(사례 C) | 세션 재수립 프로토콜과 하트비트, 이전 세션 강제 정리 |
| 스케줄러가 멈춰도 알 수 없고 배치 소급 실행이 어려움(사례 D) | 스케줄러 상태 감시와 알림, 기간 지정 소급 실행 기본 제공 |
| 장비 시각 오류로 미래 날짜 파티션 생성(사례 A) | 수신 시각 기준 저장, 장비 시각 편차는 검증해 격리 |
| 패치 후 migrate·옵션 누락(사례 A·D) | 업그레이드 시 스키마 마이그레이션과 설정 이관 자동화 |
| `_time` 변환 동작이 예고 없이 바뀜 | 쿼리 함수 하위 호환 보장, 변경 사항은 릴리스 노트에 명시 |

**성능 목표(2026-10-31 확정, PLAN.md 5장)**: 단일 x86 서버 UDP 수집·저장·인덱싱 540만 EPS 이상(기준 제품 공개 수치 270만 EPS의 2배 목표), 노드당 600GB/일 이상(Splunk 인덱서 공개 용량 300GB/일의 2배 목표, 검색 부하 동시 처리), 25억 건 이상 검색은 동일 조건에서 기준 응답 시간의 1/2 이하. 공개 수치는 시험 조건이 충분히 공개되지 않았으므로 동등 조건의 실측 전까지 달성 또는 직접 비교 성능으로 표현하지 않는다. 시험 절차는 docs/BENCHMARK_PLAN.md를 따른다.

## 5. 단계 계획
| 단계 | 내용 | 비중 |
|---|---|---|
| 0 | 착수: 기능 명세서(공개 자료 기반), 아키텍처·인터페이스 헤더, 코딩·주석 규칙, 벤치마크 계획 | 5% |
| A | 끝에서 끝까지 최소 동작: 에이전트 → 전달 → 저장 → 검색 (stage1 코드 확장) | 15% |
| B | 파이프 쿼리 언어 완성, 인덱스(역인덱스·블룸필터), 성능 최적화 | 15% |
| C | 웹 API(C), 웹 UI: 로그인·검색·수집기 관리·대시보드 | 20% |
| D | 실시간·배치 시나리오, 티켓 | 15% |
| E | 소명: 메일, 소명 페이지, 승인 워크플로 | 10% |
| F | 이상징후 탐지(행위 프로파일) | 10% |
| G | 이중화, 운영 셸, 업그레이드·마이그레이션 | 10% |

## 6. 이미 완료된 것
- `stage1/`: UDP Syslog 수집기(minilogd), 기간·키워드 조회기(minilog-query), 공통 헤더, Makefile
- 빌드 경고 0건, 2만 건 수신·저장 및 키워드 검색(200건) 테스트 통과
- 레코드 포맷: [헤더 16바이트: time_ms 8, src_ip 4, len 4][원문], 일자별 파티션 `data/<table>/YYYY-MM-DD.dat`

## 7. 팀 운영 방식
- **팀장(Claude)**: 설계, 인터페이스 헤더 확정, 작업 배정, 코드 리뷰, 통합 빌드·테스트, 진행률 보고
- **작업자(서브 에이전트)**: 단계별 모듈 담당. 예: 에이전트·전달 / 저장 엔진 / 인덱스·쿼리 / 웹 API / 웹 UI / 시나리오·소명
- 작업자는 서로 직접 소통하지 않고 팀장이 조율한다. 인터페이스(헤더)를 먼저 고정한 뒤 병렬로 개발한다.
- 산출물은 GitHub 저장소에 단계마다 커밋한다(저장소 이름은 발주자가 지정).

## 8. 진행률 표시 규칙
모든 답변의 맨 위에 다음 형식으로 전체 진행률을 표시한다.
```
[전체 진행률] ███░░░░░░░░░░░░░░░░░ 15%  | 현재: 단계 A (40%) | 다음: 단계 B
완료: 0단계 ✔ | 진행 중: A | 대기: B C D E F G
```
- 전체 진행률 = 각 단계 비중 × 그 단계 완료율의 합
- 단계 완료 기준: 기능 구현, 빌드 경고 0, 테스트 통과, 발주자 확인
