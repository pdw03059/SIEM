# MAZKION 성능 아키텍처 초안

> 상태: 설계 가설(v0.1). 아래 내용은 성능 달성 결과가 아니며, 구현 전 부하 모델·프로파일링·프로토타입으로 검증하고 발주자 승인을 받아야 한다.

## 1. 목표와 범위

| 지표 | 목표 | 검증 정의 |
|---|---:|---|
| 단일 서버 UDP 수집·저장·인덱싱 | 5,400,000 EPS 이상 | 지정 시험 시간 동안 영속화·색인 완료 이벤트 수/초, 유실 0 별도 검증 |
| 노드당 일일 수집량 | 600 GB/day 이상 | 검색 부하를 동시에 발생시키며 24시간 입력·저장 지속 |
| 대용량 검색 | 25억 건 이상에서 기준 응답 시간의 1/2 이하 | 동일 데이터·하드웨어·쿼리·캐시 조건에서 p50/p95/p99 비교 |

EPS와 GB/day는 이벤트 크기·압축·파싱·인덱스 범위가 다르므로 서로 환산하거나 같은 시험으로 대체하지 않는다. UDP 유실 0은 송신기 계수, 수신 계수, 영속화 계수의 일치와 시퀀스 번호 검증으로 확인한다.

## 2. 데이터 경로(목표 구조)

1. **수신**: UDP 수신 소켓을 CPU 코어/큐에 분산하고, 수신 스레드는 최소 검증·타임스탬프·큐잉만 수행한다.
2. **버퍼링**: 고정 상한 메모리 링 버퍼와 테이블별 독립 큐를 사용한다. 큐 포화 시 드롭·백프레셔 정책과 카운터를 명시하고 무제한 메모리 증가를 금지한다.
3. **파싱/정규화**: 원문 보존 경로와 파싱 경로를 분리 측정한다. CPU 집약 작업은 수신 스레드에서 분리하고 파서 실패가 다른 테이블을 막지 않게 한다.
4. **저장**: 여러 이벤트를 묶은 배치 쓰기, 순차 append, 시간 기반 파티션/세그먼트, 체크섬 및 복구 가능한 메타데이터를 검토한다. fsync 주기와 내구성 보장은 명시적으로 선택·측정한다.
5. **인덱싱**: 저장과 인덱싱을 분리된 파이프라인으로 구성하고 역인덱스·블룸 필터·필드 인덱스의 쓰기 증폭과 검색 이득을 측정한다. 인덱스 지연·백로그를 가시화한다.
6. **검색**: 시간 범위·파티션 프루닝 → 블룸 필터 → 역인덱스 후보 축소 → 필요한 데이터만 읽는 순서로 계획한다. 쿼리별 CPU·메모리·IO 예산과 동시성 제한을 둔다.
7. **격리**: 테이블별 쓰기 큐·오류 상태·자원 상한을 분리한다. 한 테이블의 정체·손상·쿼리 폭주가 다른 테이블 적재를 막지 않는 장애 주입 시험을 둔다.

## 3. 병렬 처리와 자원 통제

- 수신, 파싱, 저장, 인덱싱, 검색을 단계별 풀로 분리하고 큐 길이·대기 시간·처리율을 단계마다 기록한다.
- CPU affinity/NUMA 배치는 측정으로 결정한다. 코어 고정이 항상 유리하다고 가정하지 않는다.
- 메모리 풀과 큐는 상한을 가지며, OOM 대신 명시적 포화 상태·드롭/백프레셔 계측을 제공한다.
- NVMe 지속 쓰기·읽기, fsync, 파일시스템, RAID/가상화 영향을 따로 측정한다.
- 압축·암호화·파싱·필드 추출·시나리오 실행은 각각 켜고 끈 조합을 측정해 비용을 분리한다.

## 4. 병목 가설과 검증 순서

| 잠재 병목 | 관측값 | 실험 |
|---|---|---|
| NIC/UDP 수신 | NIC drop, socket drop, sequence gap | 큐·RSS·수신 스레드 수 변경 |
| CPU/파싱 | 코어별 사용률, cycles/event | 원문 저장 vs 파싱·정규화 |
| 큐 경합 | enqueue wait, queue depth | producer/consumer 수·테이블 수 변경 |
| 디스크 | MB/s, IOPS, await, fsync latency | 배치 크기·동기화 정책·장치 비교 |
| 인덱스 쓰기 증폭 | bytes indexed / bytes ingested, backlog | 인덱스 종류·필드 수·세그먼트 크기 |
| 검색 간섭 | ingest throughput, query p95/p99 | 동시 검색 수와 쿼리 유형 변화 |
| 메모리 압박 | RSS, page fault, cache hit, OOM | 데이터 규모·캐시 상한 변경 |

## 5. 설계 승인 게이트

540만 EPS 달성 가능성을 문서만으로 단정하지 않는다. 먼저 단일 노드 최소 수직 슬라이스(수신→큐→배치 저장→인덱스→검색)를 구현하고 각 단계 처리량·대기 시간·자원 사용량을 계측한다. 측정 결과가 목표에 미달하면 병목과 개선 가설을 보고하고 아키텍처 변경은 근거와 함께 검토한다. 목표 달성 전까지 '2배 성능 달성'이라고 표현하지 않는다.
