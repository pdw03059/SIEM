설계 원칙 요약(모든 장에 공통 적용)
1. **부분 장애는 부분에서 멈춘다**: 테이블·수집기·파서·규칙 하나가 깨져도 그것만 격리하고 나머지는 동작한다(L01·L09, DECISIONS 2026-10-29 테이블별 쓰기 큐).

4. **API 우선**: 화면에서 되는 모든 일은 공개 REST API로 된다. 웹 UI도 그 API만 쓴다.
5. **확장은 파일 추가로**: 새 수집기 유형·파서·쿼리 명령어·대시보드·오류 코드·API 명령·AI 공급자는 등록 표 한 줄 + 파일 하나.

## 2. 서버 역할 4종

발주자 결정(2026-10-31): 에이전트·수집 서버·전달 서버·분석 서버. 분석 서버는 수집 기능을 겸할 수 있다.

### 2-1. 역할별 책임

| 역할 | 책임 | 하지 않는 일 | 상태(디스크) |
|---|---|---|---|
| **에이전트** | 단말·서버에서 파일·Windows 이벤트·journald·프로세스 지표 수집, 원천 필터(레벨 제외, L07), 선택적 사전 파싱(PAR-008), 로컬 디스크 버퍼, 다중 목적지 전환 | 저장·색인·검색 | 로컬 버퍼(스풀), 수집 위치(체크포인트) |
| **수집 서버** | 네트워크 수신(Syslog UDP/TCP/TLS, SNMP Trap, NetFlow 등), 주기 수집(SFTP·DB·REST·Kafka·클라우드 감사), 파싱·정규화·스트림 쿼리(수집 직후 단계), 다음 단계로 전송 | 장기 저장·검색 | 수신 버퍼, 주기 수집 체크포인트 |
| **전달 서버** | 에이전트·수집 서버의 데이터를 받아 **디스크에 먼저 저장한 뒤** 분석 서버로 전달(store-and-forward), 재전송, 부하 분산·경로 선택, 백프레셔 중계 | 파싱(기본값), 저장·검색 | 전달 스풀(테이블·목적지별) |
| **분석 서버** | 테이블 저장·색인·검색·쿼리 엔진, 시나리오·티켓·소명·이상징후, 메타데이터(SQLite)·내장 인증기관·제어 평면·REST API·웹 UI 제공. **수집 겸용 가능**(수집 서버 모듈을 같은 프로세스에서 켬) | — | 테이블 세그먼트, 인덱스, SQLite, 인증기관 키(암호화) |

FEATURES.md HA-001의 3티어(전달-수집-분석) 구조를 기본 배치로 하되, 작은 현장은 "분석(수집 겸용) 1티어", 중간 현장은 "에이전트 → 전달 → 분석(수집 겸용)" 2티어로 줄일 수 있다. **역할 추가만으로 무중단 전환**(HA-009)을 목표로 한다.

### 2-2. 단일 실행 파일 + 역할 설정

- 실행 파일은 `mazkion` **하나**를 기본안으로 제안한다. 역할은 설정(`roles = ["analysis", "collector"]`)과 `mazkion init` / `mazkion join --role <역할>`으로 정한다. 에이전트는 설치 크기·권한을 줄이기 위해 같은 소스에서 **에이전트 전용 빌드**(`mazkion-agent`)를 따로 만든다. **[승인 필요]** PLAN 13장은 "역할별 정적 실행 파일 또는 한 파일 + 역할 선택"을 열어 두었다(14장 Q1).
- 프로세스 구성: 한 노드에 **감독 프로세스 1개 + 역할 작업 프로세스**. 감독 프로세스는 설정 로드·사전 점검·인증서·작업 프로세스 재시작·`sys.services` 상태 기록만 한다. 작업 프로세스(수신·저장·색인·쿼리·API)는 스레드 풀로 단계를 나눈다(7장). 쿼리 실행은 별도 작업 프로세스로 분리해, 쿼리 폭주나 파서 크래시가 수신·저장을 죽이지 않게 한다(L04).
- 각 서비스는 의존 관계를 선언하고, 기동 실패 시 **첫 원인 오류**를 `sys.errors` 맨 위에 올린다(L01). 의존 대상 하나가 실패해도 영향 없는 서비스는 기동한다.
- 메모리는 설정 1개(전체 사용 비율)로 자동 산정해 모듈별 예산을 배분한다(L05, SYS-003). 위험한 값은 기동 전에 사람 말 오류로 거부한다.

## 3. 데이터 흐름

### 3-1. 전체 경로

```
 [원천 장비·서버]
   │ Syslog UDP/TCP/TLS, SNMP, Flow          파일·이벤트 로그·journald
   ▼                                           ▼
 ┌────────────┐   mTLS, 배치+시퀀스+CRC   ┌────────────┐
 │ 수집 서버  │──────────────┐            │  에이전트  │ 로컬 스풀
 │ 수신·파싱  │              │            └─────┬──────┘
 └────────────┘              ▼                  │ mTLS, 배치+시퀀스
                       ┌──────────────┐◄────────┘
                       │  전달 서버   │  ① 디스크 스풀에 저장(fsync 그룹 커밋)
                       │ store-and-   │  ② 저장 후 ACK
                       │ forward      │  ③ 분석 서버로 재전송·부하 분산
                       └──────┬───────┘
                              │ mTLS, 배치+시퀀스(종단 ID 유지)
                              ▼
 ┌─────────────────────────── 분석 서버 ───────────────────────────┐
 │ 수신 → 중복 제거 → 테이블별 쓰기 큐 → 세그먼트 저장 → 색인(비동기) │
 │                                    │                      │      │
 │                         SQLite(메타) │         역인덱스·블룸필터  │
 │ 쿼리 엔진: 시간 프루닝 → 블룸 → 역인덱스 → 필요한 블록만 읽기     │
 └──────────────────────────────┬──────────────────────────────────┘
                                ▼
                REST API ── 웹 UI / CLI / n8n / 외부 연동
```

### 3-2. 전송 단위와 신뢰성

| 항목 | 설계 |
|---|---|
| 전송 단위 | **배치**(여러 이벤트 묶음). 배치 헤더: 프로토콜 버전, 송신 노드 ID, 스트림 ID(수집기·테이블별), **배치 시퀀스 번호(64비트, 스트림 안에서 단조 증가)**, 이벤트 수, 압축 방식, 본문 길이, CRC32C (FWD-001) |
| 보장 수준 | **최소 1회 전달 + 시퀀스 기반 중복 제거 = 사실상 정확히 1회**(FWD-004). UDP 원천은 송신 장비가 재전송하지 않으므로 "수집 서버가 받은 뒤부터" 이 보장이 적용된다 |
| 저장 후 전달 | 전달 서버와 에이전트는 받은 배치를 **디스크 스풀에 쓴 뒤(fsync 그룹 커밋) ACK**한다. 다음 홉의 ACK를 받아야 스풀에서 지운다. 스풀은 테이블·목적지별로 나눠 한 목적지 장애가 다른 목적지를 막지 않는다 |
| 재전송 | 연결이 끊기면 ACK 안 된 가장 작은 시퀀스부터 다시 보낸다. 재전송 간격은 지수 백오프+무작위 지터, 상한 있음. `retransmits_24h` 집계 |
| 중복 제거 | 수신 측은 (송신 노드 ID, 스트림 ID)마다 **마지막으로 영속화한 시퀀스 번호(고수위 표시)**를 SQLite가 아닌 세그먼트 메타에 함께 기록한다. 그보다 작거나 같은 배치는 버리고 `duplicates_24h`를 올린다. 영속화와 고수위 갱신은 같은 쓰기 단위로 처리해 재시작 후에도 맞는다 |
| 종단 추적 | 배치에 원천 노드 ID·원천 시퀀스를 그대로 실어, 분석 서버에서 `forward_path`(에이전트 → 전달 → 분석)와 `recv_vs_stored_diff_24h`를 계산한다 |
| 시각 | 파티션은 **수신 시각(UTC)** 기준, 원본 이벤트 시각은 별도 필드. 허용 편차 밖은 격리 파티션 + 경보(STO-002, L15) |

### 3-3. 백프레셔

- 모든 큐와 스풀은 **상한**이 있다. 무제한 메모리 증가는 금지(PR #5).
- 테이블별 쓰기 큐가 차면 그 테이블만 느려진다: ① 분석 서버가 해당 스트림의 ACK 창(window)을 줄인다 → ② 전달 서버는 그 테이블의 배치만 디스크 스풀에 쌓는다 → ③ 스풀이 상한에 가까우면 상위(에이전트·수집 서버)에 창 축소를 전파한다 → ④ 에이전트는 로컬 스풀에 쌓는다. 다른 테이블 흐름은 그대로 유지(FWD-007).
- UDP 수신은 송신 측을 늦출 방법이 없으므로, 수신 링이 차면 **버리고 반드시 센다**(`dropped_queue_full_24h`, `udp_kernel_drops_24h`). "보이지 않는 유실"을 없애는 것이 목표다.
- 대기 원인(잠금 대기·디스크 지연·복제 대기·색인 적체)은 `write_wait_reason`, 가장 오래 기다린 데이터 나이는 `buffer_oldest_age_sec`로 실시간 표시(L15).

## 4. 모든 역할의 이중화 — [승인 필요]

발주자 결정(2026-10-31): 수집·전달·분석(수집 겸용 포함) 모든 역할이 이중화 가능해야 하며, 방식은 역할별로 이 문서에서 제안해 승인받는다. 이 장 전체가 승인 대상이다.

### 4-1. 역할별 제안

| 역할 | 제안 방식 | 복제할 상태 | 장애 감지·전환 목표 [목표] | split-brain 방지 |
|---|---|---|---|---|
| 에이전트 | 이중화 대상 아님(원천 장비 자체). 대신 **다중 목적지**(4-2) | 로컬 스풀·체크포인트(복제 안 함) | 목적지 전환 10초 이내 | 해당 없음(중복은 시퀀스로 제거) |
| 수집 서버 — 수신형(Syslog·Trap·Flow) | **활성-대기 + 가상 IP**(VRRP 계열). 원천 장비가 목적지 1개만 지정할 수 있는 경우가 많기 때문 | 수집기 설정(제어 평면이 배포, 복제 불필요), 수신 통계 | 감지 3초, VIP 이동 5초 이내. 전환 중 UDP 유실은 측정·표시 | VIP 소유는 분석 서버의 **임대(lease)**와 함께 확인. 임대를 못 받으면 VIP를 내려놓음 |
| 수집 서버 — 주기 수집형(SFTP·DB·REST·Kafka) | **활성-활성 노드 + 수집기별 단일 실행자**. 수집기마다 실행 노드 1개를 임대로 배정 | **체크포인트**(파일 위치·DB 기준 값·Kafka 오프셋)를 분석 서버에 커밋 | 임대 만료 30초 후 다른 노드가 인계 | 임대에 **세대 번호(fencing token)**. 낡은 세대의 데이터·체크포인트 커밋은 분석 서버가 거부 |
| 전달 서버 | **활성-활성**(N대). 에이전트·수집 서버가 목적지 목록으로 분산·전환 | 스풀은 복제하지 않음(제안). 송신 측이 ACK 전까지 보관하므로 유실 없음. 단, 전달 서버 디스크가 영구 손실되면 그 서버가 ACK한 미전달분은 잃는다 → 14장 Q4 | 송신 측 전환 10초 이내 | 상태가 없으므로 불필요. 중복은 시퀀스로 제거 |
| 분석 서버(수집 겸용 포함) | **활성-대기**. 자체 변경 로그 복제(DECISIONS 2026-10-30) | SQLite 변경 로그, 테이블 세그먼트(완성 세그먼트 단위 전송 + 열린 세그먼트의 변경 로그), 인덱스(대기 쪽 재생성 또는 전송 — 측정 후 결정), 래핑된 테이블 키·인증기관 키 | 감지 10초, 전환 60초 이내. 복제 지연(건수·초)은 `sys.replication` | **증인(witness) 노드**를 둔 3표 과반. 증인은 수집·전달 서버 중 하나가 겸할 수 있음. 활성은 과반 임대를 잃으면 즉시 쓰기 중지. 모든 쓰기·복제 메시지에 세대 번호 |
| 제어 평면 | 분석 서버를 따라감 | 인증기관 상태, 발급·폐기 목록, 감사 로그 | 분석 서버와 동일 | 분석 서버와 동일 |

보충
- 분석 서버 활성-활성(쓰기 분산)은 데이터 규모가 단일 노드를 넘는 경우의 **확장** 문제로 보고, 이중화와 분리해 G단계 이후 분산 쿼리(HA-005)와 함께 설계한다.
- 이중화 구성은 `mazkion init --ha` 또는 웹 "대기 노드 추가" 한 번으로 복제 연결·초기 동기화·**전환 시험**까지 자동 수행(PLAN 13장).
- 2노드만으로는 split-brain을 원리적으로 막을 수 없다. 증인 없는 2노드 구성을 허용할지, 허용 시 자동 전환을 끌지(수동 전환만) 결정 필요(14장 Q3).

### 4-2. 에이전트의 다중 목적지

- 설정: 목적지 목록(전달 서버·수집 서버·분석 서버 중 무엇이든), 모드 `failover`(우선순위 순) 또는 `balance`(가중치 분산). 기본 `failover`.
- 전환 조건: 연결 실패, 하트비트 시간 초과, ACK 지연이 임계 초과. 원래 목적지가 회복되면 일정 시간 안정 확인 후 복귀(깜빡임 방지).
- 전환해도 ACK 안 된 배치는 새 목적지로 다시 보낸다. 분석 서버의 시퀀스 중복 제거가 같은 배치가 두 경로로 도착한 경우를 정리한다.
- 같은 에이전트 ID가 새로 인증하면 이전 세션을 즉시 교체(세션 인수, L02). 상태는 "연결됨"이 아니라 "데이터가 실제로 흐르는가"로 판정(`connected_no_data`).

### 5-1. 기능

| 기능 | 내용 |

| 조회 | 노드·에이전트 목록, 역할, 버전, OS, 상태, 연결 경로(`forward_path`), 인증서 만료, 설정 버전·해시 불일치 — `sys.nodes`, `sys.agents`, `sys.forwarders`, `sys.collectors` |

### 5-2. 제어 채널

```
 분석 서버(제어 평면 + 내장 인증기관)
   ▲  ▲                         ▲
   │  │ mTLS (노드 인증서)       │ mTLS (에이전트 인증서)
   │  └── 전달 서버 ◄────────────┘ 에이전트는 바깥으로만 연결(들어오는 포트 없음)
   └───── 수집 서버                 제어 명령은 에이전트가 연 연결로 전달(끌어오기)
```

| 항목 | 설계 |
|---|---|
| 노드 인증 | **상호 TLS**(TLS 1.2 이상, 1.3 기본). 분석 서버 `init` 시 **내장 인증기관**을 만들고 노드별 인증서를 자동 발급. 저장된 관리자 암호로 노드를 인증하지 않음(L06) |
| 참여 | `mazkion init`이 **참여 토큰** 발급(일회용·짧은 유효 기간·역할 제한). 토큰에는 인증기관 공개키 지문이 들어 있어 참여 노드가 처음 연결할 때 서버를 검증(신뢰 고정). 참여 노드가 키 쌍을 직접 만들고 서명 요청만 보냄(개인키는 노드 밖으로 나가지 않음) |
| 인증서 수명 | 짧은 수명 + 만료 전 자동 갱신, 무중단 교체. 폐기 목록은 제어 평면이 배포. 만료일은 `sys.nodes`에 표시 |
| 경로 | 에이전트 → 전달 서버 → 분석 서버처럼 직접 연결이 없으면 제어 메시지는 **데이터 경로를 따라 중계**한다. 중계 노드는 내용을 바꿀 수 없다(명령은 분석 서버가 서명) |
| 권한 | 역할 기반 접근 제어. 예: `viewer`(조회), `collector_admin`(수집기 설정·시작·중지), `node_admin`(업그레이드·노드 제거), `security_admin`(인증서·키). 사람·API 키 모두 같은 권한 모델(9장) |
| 명령 재생 방지 | 모든 제어 명령에 명령 ID(UUID), 대상 노드 ID, 발급 시각, 만료 시각, 대상별 단조 증가 번호, 분석 서버 서명. 대상은 이미 처리한 번호 이하·만료된 명령·다른 대상 명령을 거부 |
| 감사 | 누가·언제·어느 노드에·무엇을·결과를 `sys.audit`에 기록. 감사 로그도 해시 체인(6-4)으로 위변조 검증 |
| 시간 초과 | 모든 RPC는 연결·응답 시간 초과와 재시도 상한을 가진다. 무한 대기 금지(HA-006) |

## 6. 저장 포맷

### 6-1. 계층

```
<data_root>/
  meta/mazkion.db                    ← 내장 SQLite: 설정·사용자·권한·수집기·시나리오·티켓·소명·키 래핑 정보
  tables/<table_id>/                 ← 테이블 번호의 단일 출처는 이 디렉터리의 manifest(L01)
    manifest                         ← 테이블 ID·이름·포맷 버전·저장 정책 버전·해시 체인 머리
    p=2026-11-01/                    ← 시간 파티션(수신 시각 UTC, 일 단위 기본)
      seg-000001.mzs                 ← 세그먼트(불변, 크기·시간 상한 도달 시 닫힘)
      seg-000001.blm                 ← 블록별 블룸 필터
      seg-000001.inv                 ← 역인덱스(용어 사전 + 압축 포스팅)
      seg-000001.fidx                ← 필드 인덱스(숫자·IP·시각 범위)
    quarantine/                      ← 시각 이상 격리 파티션
  spool/                             ← 전달·에이전트 스풀(테이블·목적지별)
```

- 테이블 ID는 생성 시 부여되는 불변 UUID, 이름은 바꿀 수 있다(SYSTEM_VIEWS 공통 규칙).
- 기동 자가 점검에서 manifest와 SQLite가 어긋난 테이블은 **그 테이블만 격리**하고 나머지는 기동한다(L01).

### 6-2. 세그먼트 구조

```
[세그먼트 헤더] magic "MZKSEG" | 포맷 버전(u16) | 헤더 길이 | 플래그 | 테이블 ID | 세그먼트 번호
               | 생성 시각 | 압축 알고리즘·수준 | 암호화 키 ID(없으면 0) | 헤더 CRC32C
[블록 1..N]    블록 헤더: 건수, 최소·최대 수신 시각, 원문·압축 크기, 첫 레코드 번호, CRC32C
               블록 본문: 압축(→ 암호화) 된 레코드 묶음 (원문 + 정규화 필드, PAR-001)
[꼬리]         블록 위치 표, 송신 스트림별 고수위 시퀀스(3-2), 이전 세그먼트 해시,
               이 세그먼트 해시, 꼬리 CRC32C, 꼬리 길이, magic
```

- 블록 안의 배치는 행 묶음 안에서 필드별 열(column) 배치를 기본안으로 한다(필드 필터 시 필요한 열만 풀기). 원문 열은 항상 보존.
- 포맷 버전은 세그먼트·인덱스·스풀·통신 배치·설정 묶음마다 **각각** 둔다(CLAUDE.md "저장 포맷·통신 메시지에는 버전 번호").
- 열린(쓰는 중) 세그먼트는 꼬리가 없으므로, 재시작 시 블록 CRC로 마지막 완전한 블록까지 복구하고 이후는 잘라낸다.

### 6-3. 테이블 단위 정책(PLAN 10-1)

| 정책 | 설계 | 적용 시점 |
|---|---|---|
| 압축 | 테이블별 lz4 / zstd 1~19. 블록 단위 압축. 변경은 다음 세그먼트부터 | B |
| 암호화 | 테이블별 AES-256-GCM, **압축 후 암호화**. 블록마다 고유 논스. 테이블 데이터 키를 마스터 키로 감싸(봉투 암호화) SQLite에 보관. 키 교체 시 새 데이터는 새 키, 옛 데이터는 백그라운드 재암호화. 암호 모듈은 인터페이스 뒤에 두어 검증필 모듈(KCMVP)로 교체 가능 | B |
| 위변조 방지 | 6-4 해시 체인 | B |
| 생명주기 | 뜨거움 → 따뜻함 → 차가움 → 보관(외부·오브젝트 저장소) → 삭제. 파티션 단위 이동은 "복사 → 검증 → 원본 삭제" 순서. 법적 보존 잠금 시 삭제 금지. 모든 이동·삭제 감사 | B(이동), G(외부 계층) |
| 보존 | 테이블별 기간, 삭제 예정 미리보기, 디스크 고갈 단계 정책(경보 → 오래된 것 삭제 → 수집 중단, STO-008) | A |

### 6-4. 해시 체인

- 세그먼트 해시 = SHA-256(헤더 ‖ 모든 블록의 **저장된 바이트**(암호화 후) ‖ 꼬리의 해시 제외 부분). 저장된 바이트에 대해 계산하므로 **키 없이도** 검증 가능.
- 체인: `H_n = SHA-256(H_(n-1) ‖ 세그먼트 해시_n)`, 테이블마다 하나. 체인 머리는 manifest와 SQLite에 이중 기록하고, 일 단위로 노드 키 서명 체크포인트를 남긴다(STO-010).
- 검증 결과는 `sys.tables.hash_chain_ok`·`last_verified_at`. 백업 검증(10-2)에도 같은 해시를 쓴다.

### 6-5. 메타데이터(SQLite)

- 노드마다 내장 SQLite 1개, 외부 DB 없음. 쓰기는 한 작성자 스레드(직렬화), 읽기는 WAL 모드 동시 읽기.
- `schema_version` 표 + 순번 마이그레이션 파일. **기동 시 자동 마이그레이션**, 실행 전 백업, 실패 시 되돌리기(L09).
- 분석 서버 이중화 복제는 SQLite 파일 복사가 아니라 **자체 변경 로그**(행 단위 변경 기록, 세대 번호 포함)로 한다.
- 대규모 클러스터용 외부 PostgreSQL은 선택 기능으로만 검토(DECISIONS 2026-10-30).

### 6-6. 인덱스 위치

| 인덱스 | 위치 | 용도 |
|---|---|---|
| 시간 범위 | 세그먼트 헤더·블록 헤더 | 파티션·세그먼트·블록 프루닝 |
| 블룸 필터 | 세그먼트 옆 `.blm`, 블록 단위 | 없는 키워드는 블록을 열지 않음 |
| 역인덱스 | 세그먼트 옆 `.inv`, 세그먼트 단위 | 용어 → (블록, 레코드) 포스팅 |
| 필드 인덱스 | 세그먼트 옆 `.fidx` | 숫자·IP 대역·시각 범위 질의 |

인덱스는 세그먼트에서 언제든 다시 만들 수 있는 **파생물**이다. 그래서 손상 시 재생성, 과거 파티션 백그라운드 재색인(IDX-008), 대기 노드 재생성이 가능하다.

### 6-7. 마이그레이션 원칙

1. 포맷을 바꾸면 버전 번호를 올리고, **읽기는 이전 버전 전부 지원**, 쓰기는 최신 버전만.
2. 변환이 필요하면 백그라운드 재작성(복사 → 검증 → 교체), 진행률은 `sys.tables`.
3. 구버전 데이터 호환 시험(고정 시험 세그먼트)을 업그레이드 시험에 포함(L10). 이관 도구는 ID 대응표를 만들고 건수·해시로 검증 보고(L12).

| 단일 x86 서버 UDP 수집·저장·인덱싱 | 5,400,000 EPS 이상 | 시험 시간 동안 영속화·색인 완료 이벤트 수/초, 유실 0 별도 검증 |
| 노드당 일일 수집량 | 600 GB/일 이상 | 검색 부하를 동시에 발생시키며 24시간 입력·저장 지속 |
| 대용량 검색 | 25억 건 이상에서 기준 응답 시간의 1/2 이하 | 동일 데이터·하드웨어·쿼리·캐시 조건에서 p50/p95/p99 비교 |
| 장애 격리 | 한 테이블 장애가 다른 테이블 적재에 영향 없음 | 장애 주입 시험(BENCHMARK_PLAN D) |

EPS와 GB/일은 이벤트 크기·압축·파싱·인덱스 범위가 다르므로 **서로 환산하거나 같은 시험으로 대체하지 않는다**. UDP 유실 0은 송신기·수신·영속화 계수 일치와 시퀀스 번호 검증으로 확인한다.

### 7-2. 데이터 경로(목표 구조)

1. **수신**: UDP 수신 소켓을 CPU 코어·NIC 큐에 분산(SO_REUSEPORT, RSS)하고, 수신 스레드는 최소 검증·타임스탬프·큐잉만 한다. 한 번의 시스템 호출로 여러 패킷 받기(recvmmsg)를 기본으로 측정한다.
2. **버퍼링**: 고정 상한 메모리 링 버퍼와 테이블별 독립 큐. 큐 포화 시 드롭·백프레셔 정책과 카운터를 명시하고 무제한 메모리 증가를 금지한다.
3. **파싱·정규화**: 원문 보존 경로와 파싱 경로를 분리 측정한다. CPU 집약 작업은 수신 스레드에서 떼어 내고, 파서 실패가 다른 테이블을 막지 않게 한다.
4. **저장**: 배치 쓰기, 순차 추가(append), 시간 파티션·세그먼트, 체크섬과 복구 가능한 메타데이터. fsync 주기와 내구성 보장은 명시적으로 선택·측정한다.
5. **인덱싱**: 저장과 분리된 파이프라인. 역인덱스·블룸 필터·필드 인덱스의 쓰기 증폭과 검색 이득을 측정하고, 인덱스 지연·적체를 가시화한다.
6. **검색**: 시간 범위·파티션 프루닝 → 블룸 필터 → 역인덱스 후보 축소 → 필요한 데이터만 읽기. 쿼리별 CPU·메모리·I/O 예산과 동시성 제한(L04).
7. **격리**: 테이블별 쓰기 큐·오류 상태·자원 상한을 분리하고, 한 테이블의 정체·손상·쿼리 폭주가 다른 테이블 적재를 막지 않는지 장애 주입 시험을 둔다.

병렬 처리와 자원 통제(PR #5 원문 유지)
- 수신·파싱·저장·인덱싱·검색을 단계별 풀로 분리하고 큐 길이·대기 시간·처리율을 기록한다.
- CPU 고정(affinity)·NUMA 배치는 측정으로 결정한다. 코어 고정이 항상 유리하다고 가정하지 않는다.
- 메모리 풀과 큐는 상한을 가지며, 포화·드롭·백프레셔를 계측한다.
- NVMe 지속 쓰기·읽기, fsync, 파일시스템, RAID·가상화 영향을 따로 측정한다.
- 압축·암호화·파싱·필드 추출·시나리오 실행은 각각 켜고 끈 조합으로 측정해 비용을 분리한다.
- 성능 때문에 복잡하게 쓴 코드는 별도 파일로 분리하고 이유와 벤치마크 수치를 주석으로 남긴다(CLAUDE.md).

### 7-3. 달성 가능성 추정(봉투 뒷면 계산) — 모든 값 [가정]

기준 하드웨어 가정: 실험 서버 권장 사양(DECISIONS 2026-10-30) **16코어·64GB·NVMe 2TB**, 3GHz. 이벤트 평균 크기 **200바이트**, 이벤트 1건 = UDP 패킷 1개. 단일 x86 서버의 실제 사양은 PLAN 5장에 정해져 있지 않다(14장 Q6).

| 항목 | 계산 | 결과 [가정] | 측정할 것 |
|---|---|---|---|
| 원문 유입량 | 5,400,000 × 200 B | **1.08 GB/s**(약 8.6 Gbps) | 이벤트 크기 분포(최소 3구간) |
| 회선 | 패킷당 이더넷·IP·UDP 부가 약 42 B 더하면 5.4M × 242 B × 8 | **약 10.5 Gbps** → 10GbE 한 줄로 부족, **25GbE 이상** 필요 | NIC 드롭, 큐 수 |
| 패킷률 | 5.4M pps. 코어당 recvmmsg 수신 능력을 1~1.5M pps로 가정 | 수신에만 **4~6코어** | 코어별 pps, 소켓 드롭 |
| 코어당 예산 | 5.4M ÷ 16코어 | **337,500 EPS/코어 ≈ 2.96 µs/건 ≈ 약 8,900 사이클/건**(전 단계 합계) | cycles/event(단계별) |
| 같은 예산, 32코어 | 5.4M ÷ 32 | 168,750 EPS/코어 ≈ 5.9 µs/건 | — |
| 디스크 쓰기 | 압축률 lz4 4배 가정 → 1.08 ÷ 4 = 0.27 GB/s, 인덱스 증폭(압축 데이터의 0.3~1.0배) 더해 | **약 0.35~0.55 GB/s** 지속 쓰기 | NVMe 지속 쓰기(SLC 캐시 소진 후), fsync 지연 |
| 메모리 대역 | 바이트당 4~6회 접근(수신 복사·파싱·압축·토큰화) | 약 4.3~6.5 GB/s | 메모리 대역·캐시 적중 |
| 색인 | 이벤트당 토큰 20개 가정 → 1억 800만 토큰/초. 토큰 해시 삽입 50~100 ns/개 가정 | **5.4~10.8 코어 분량** → **가장 유력한 병목** | 블록 내 고유 토큰 비율, 토큰당 비용 |
| 시험 디스크 소요 | 30분 시험: 1.08 GB/s × 1,800 s = 1.94 TB 원문 → 압축 4배면 약 0.49 TB + 인덱스 | 2TB NVMe에 30분 시험 수용 가능, 24시간 지속은 불가 | — |

추정에서 읽히는 것
1. **수신 + 압축 + 순차 쓰기만으로는** 16코어에서 예산 안에 들어올 가능성이 있다(수신 4~6코어 + 압축 lz4 코어당 약 0.5~0.8 GB/s 가정 시 2코어 안팎).
2. **색인이 예산을 가장 많이 먹는다.** 대응 가설: ① 로그는 반복이 많으므로 블록 안에서 토큰을 먼저 중복 제거한 뒤 사전에 넣는다(고유 토큰 비율이 10%라면 비용 1/10) ② 수집 경로에서는 블룸 필터만 동기로 만들고, 역인덱스는 세그먼트가 닫힌 뒤 정렬 기반으로 일괄 생성(비동기, 적체 가시화) ③ 테이블별 색인 대상 필드 제한.
3. **파싱·정규화를 켜면** 정규식 비용이 건당 수 µs일 수 있어 같은 예산에 들어오기 어렵다. 그래서 PLAN 5장도 "실사용 지표(파싱 포함 EPS)는 별도 확정"으로 나눴다. 540만 EPS 시험은 BENCHMARK_PLAN A의 단계(수신만 → +저장 → +색인 → +파싱)대로 각각 보고한다.
4. **1.08 GB/s를 24시간 지속하면 원문 약 93 TB/일**이다. 따라서 540만 EPS는 **최대 처리 능력(시험 시간 30분·3회, 24시간 안정성 별도)**의 지표이고, 600 GB/일(평균 약 6.9 MB/s, 200 B 기준 약 3만 5천 EPS)은 **검색 부하와 함께 24시간 버티는 지속 운영** 지표다. 두 목표는 서로 다른 것을 재며 모순이 아니다(7-1 환산 금지 원칙).
5. **검색 25억 건**: 200 B 기준 원문 500 GB, 압축 4배면 약 125 GB. 전체 스캔은 NVMe 읽기 3 GB/s 가정 시 약 40초 이상이므로, 밀리초 단위 응답은 **희귀 키워드 + 블룸·역인덱스로 읽을 블록을 줄이는 경우**에만 기대할 수 있다. 흔한 키워드는 "첫 결과 시간"과 "전체 완료 시간"을 나눠 보고한다(BENCHMARK_PLAN C).
6. **문자열 처리 가속(SIMD 등)**은 기준 제품 등록 특허가 있으므로 구현 전 특허 회피 검토가 필수다(PLAN 5장). 추정은 SIMD 없이 세웠다.

### 7-4. 병목 가설과 검증(PR #5)

| 잠재 병목 | 관측값 | 실험 |
|---|---|---|
| NIC·UDP 수신 | NIC 드롭, 소켓 드롭, 시퀀스 틈 | 큐·RSS·수신 스레드 수 변경 |
| CPU·파싱 | 코어별 사용률, cycles/event | 원문 저장 vs 파싱·정규화 |
| 큐 경합 | 넣기 대기, 큐 깊이 | 생산자·소비자 수, 테이블 수 변경 |
| 디스크 | MB/s, IOPS, await, fsync 지연 | 배치 크기·동기화 정책·장치 비교 |
| 인덱스 쓰기 증폭 | 색인 바이트 / 수집 바이트, 적체 | 인덱스 종류·필드 수·세그먼트 크기 |
| 검색 간섭 | 수집 처리율, 쿼리 p95/p99 | 동시 검색 수와 쿼리 유형 변화 |
| 메모리 압박 | RSS, 페이지 폴트, 캐시 적중 | 데이터 규모·캐시 상한 변경 |

### 7-5. 설계 승인 게이트(PR #5)

540만 EPS 달성 가능성을 문서만으로 단정하지 않는다. 먼저 **단일 노드 최소 수직 슬라이스(수신 → 큐 → 배치 저장 → 인덱스 → 검색)**를 구현하고 각 단계 처리량·지연·자원 사용량을 계측한다. 미달이면 병목과 개선 가설을 보고한다. 측정 절차·환경 기록·보고 형식은 `docs/BENCHMARK_PLAN.md`(PR #5)를 따른다. 결과 표현은 "목표/미검증 → 단독 실측 → 동일 조건 비교 → 재현"의 4단계를 지킨다.

## 8. 통합 시스템 뷰(sys.*)·자동 등록 대시보드·오류 기록

### 8-1. sys.* 뷰 구조

명세는 `docs/SYSTEM_VIEWS.md`가 기준이다. 여기서는 만드는 방식만 정한다.

| 구성 | 설계 |
|---|---|
| 뷰 공급자 | 객체 종류마다 모듈이 **뷰 공급자**를 등록 표에 한 줄로 등록: 뷰 이름, 열 정의(이름·타입·단위·설명), 행을 채우는 함수. 열 정의에서 쿼리 매뉴얼·OpenAPI 스키마가 자동 생성됨 |
| 값의 출처 | ① 설정·식별 열: SQLite ② 실시간 열(eps_1m, buffer_oldest_age_sec 등): 각 모듈의 **지표 등록소**(모듈 컨텍스트 안의 카운터, 전역 변수 아님) ③ 기간 집계 열(_7d, _30d): 1분 단위 지표를 내부 테이블 `sys_metrics`에 저장해 계산 |
| 원격 객체 | 수집·전달 서버·에이전트의 열은 하트비트(기본 10초 [가정])로 분석 서버에 모은다. 하트비트가 끊기면 마지막 값과 `stale` 표시 |
| 조회 경로 | 쿼리 언어 `sys.collectors where …`, REST `GET /api/v1/sys/collectors`, 웹 UI, 기본 대시보드가 **같은 공급자**를 읽는다 |
| 비밀값 | 뷰 열 정의에 `secret` 타입을 둘 수 없게 등록 단계에서 막는다. 만료일·마지막 성공 시각만 노출 |
| 용량 지표 구분 | 원본 바이트·저장 직렬화 바이트·압축 후 바이트·라이선스 계산 바이트를 이름을 구분해 나란히 둔다(L03) |

### 8-2. 객체 생성 시 대시보드 자동 등록

- 객체 종류마다 **기본 대시보드 템플릿**을 등록 표로 선언한다(예: 수집기 → SYSTEM_VIEWS 3장의 8개 화면).
- 대시보드는 객체를 하나씩 복사해 넣지 않고 "객체 종류 = 수집기 전체" 같은 **집합 질의**로 그린다. 그래서 객체를 만들면 다음 갱신에서 자동으로 나타나고, 지우면 사라진다. 상세 페이지는 객체 ID를 인자로 받는 템플릿 하나.
- 객체 생성·삭제·이름 변경은 내부 **객체 수명 이벤트**로 발행되고, 대시보드·`sys.dependencies`·알림 규칙이 이를 구독한다. ID 기준으로 묶으므로 이름을 바꿔도 끊기지 않는다.
- 사용자 대시보드는 기본 대시보드를 복제해 고치되, 기본 템플릿 갱신은 업그레이드 때 덮어쓰고 사용자 확장은 보존한다(PAR-010과 같은 원칙).

### 8-3. sys.errors 오류 기록 형식

| 필드 | 내용 |
|---|---|
| code | `MZK-<모듈>-<4자리>`(예: `MZK-COL-0103`). 모듈별 오류 정의 파일 **한 곳**에서 정의, 매뉴얼 페이지 자동 생성 |
| severity | info / warn / crit |
| summary | "무엇이 / 왜 / 어디서" 한 문장(한국어, 영어 병기). 정의 파일의 문장 틀에 객체 이름을 끼움 |
| impact | 멈추거나 늦어지는 것(수집 중단·탐지 공백·유실 가능). `sys.dependencies`로 영향 객체 수를 자동 계산 |
| causes / actions / check_query | 가능성 높은 순 원인 후보, 조치, 확인용 쿼리 |
| objects | 관련 객체 id·이름(수집기·테이블·노드·사용자), node |
| trace_id | 같은 사건의 로그를 묶는 추적 ID(배치·명령·쿼리 ID에서 이어받음) |
| first_at / last_at / count | 반복 묶기: (code, 관련 객체) 키로 1건으로 묶고 횟수만 증가 |
| resolved | 해결 여부(조건 회복 시 자동, 또는 사람이 표시) |
| tech_detail | errno·시스템 호출·스택(접힌 칸, 개발자용) |

내부 API 개념: 모듈은 문자열을 직접 만들지 않고 `오류 코드 + 객체 + 기술 상세`만 넘긴다. 형식 조립·반복 묶기·저장은 오류 모듈이 맡는다. 기동 실패 시 첫 원인 오류를 맨 위에 고정(L01).

### 8-4. sys.dependencies

- 쿼리·시나리오·예약 쿼리·스트림 쿼리·대시보드 위젯·보고서·알림·플레이북·소명 규칙·API 키를 저장하거나 바꿀 때 **쿼리 파서가 테이블·데이터셋 참조를 추출**해 간선(from → to, relation: reads/writes/enriches/trains/triggers)을 갱신한다.
- SQLite 표 하나에 간선을 두고, 간접 깊이는 조회 시 계산(작은 그래프 가정, 객체 수만 단위에서 측정 필요).
- 사용처: 변경·삭제 전 영향 분석 경고, 탐지 공백 원인 역추적, 고아 객체 목록, 모든 뷰의 `dep_*` 열.

## 9. API 우선 구조

### 9-1. 명령 등록 표 하나에서 전부 생성

```
명령 등록 표(한 줄 = 기능 하나)
  이름 | HTTP 방식·경로 | 입력 스키마 | 출력 스키마 | 필요 권한 범위 | 감사 여부 | 동기/비동기 | 처리 함수
        │
        ├─► REST 라우터 (/api/v1/…)
        ├─► OpenAPI 명세 (빌드 시 자동 생성 → 웹 UI 타입·Python/Go 클라이언트·n8n 노드 생성)
        ├─► 명령줄 도구 (mazkion api …)
        └─► 매뉴얼 페이지
```

- 웹 UI도 이 공개 API만 쓴다(화면 전용 숨은 기능 없음). 사람이 쓰는 웹 세션과 API 키는 **같은 권한 검사**를 거친다.
- 버전: 경로에 `/api/v1`. 하위 호환을 깨는 변경은 `v2`로, 이전 버전은 정해진 기간 유지. 동작 변경은 릴리스 노트에 별도 표시(L14).
- 대용량: 쿼리 결과 스트리밍(NDJSON)·페이지 처리, 오래 걸리는 작업은 작업 ID로 상태 조회.
- 설정을 코드처럼: 수집기·시나리오·대시보드를 파일로 내보내기/가져오기(같은 스키마 사용).

### 9-2. 인증·권한·감사

| 항목 | 설계 |
|---|---|
| API 키 | 범위(scope)·만료·IP 제한. 키 원문은 발급 때 한 번만 보여 주고 서버에는 해시만 저장 |
| OAuth2 | 클라이언트 자격 방식 |
| 범위 예 | `read:sys`, `read:query`, `write:collectors`, `write:scenarios`, `exec:actions.read`, `exec:actions.change`, `admin:nodes` |
| 감사 | 모든 쓰기 호출과 민감 읽기(원문·개인정보 조회)를 `sys.audit`에 기록, 키별 호출 수·거부 수는 `sys.api_keys` |
| 호출량 제한 | 키·사용자별 제한, 쿼리는 비용 상한(L04) |

### 9-3. 웹훅·외부 연동기·액션

- **웹훅(나가는 이벤트)**: 알림·티켓·수집기 상태 변화. 본문 HMAC 서명 + 시각(재생 방지), 재시도(지수 백오프), 실패 이력 보관.
- **연동기(PLAN 16-2)**: 설정 파일 템플릿 하나 = 연동 하나(기본 URL·인증 방식·주기·페이지 규칙·응답 필드 매핑). 결과는 테이블(이력) 또는 조회용 데이터셋. 실패 단계(DNS·프록시·TLS·인증·형식)를 구분한 오류(L11). `sys.integrations`.
- **액션(PLAN 16-3)**: 연동기마다 동작 등록(이름·HTTP 방식·경로·입력·결과 매핑, **조회/변경 구분**). 호출 지점: 쿼리 명령(`ext`), 시나리오, 플레이북, 화면 버튼, API·n8n. 변경 동작은 동작별 권한·승인(사람/정책)·사전 시험·횟수 제한·되돌리기 동작 연결·감사. `sys.integration_actions`.
- **허용 목록**: 등록된 연동기·동작의 주소만 호출 가능. 임의 URL 호출 금지, 사설 대역·메타데이터 주소 차단(SSRF, PLAN 14장). 쿼리 언어에는 OS 명령 실행이 없다.

## 10. AI 인터페이스

### 10-1. 원칙(PLAN 11·12장)

1. **결정적 알고리즘 우선**: 형식 판별·템플릿 추출(Drain 계열)·타입 추론·파서 생성은 폐쇄망에서도 도는 C 코드가 먼저 한다. AI는 선택 보조.
2. **로그 1건마다 모델을 돌리지 않는다**: 새 로그 유형이 나타날 때만 생성하고, 결과(파서·매핑)는 캐시해 C 파서가 처리.
3. **검증 통과 시에만 적용**: 모든 AI 제안은 같은 검증(파서 적용률·필드 정확도 99% 이상, 백테스트·합성 공격·그림자 모드, 문법 검사·실행 비용 상한)을 통과해야 하며, 순서는 "제안 → 검증 수치 표시 → 사람 승인(또는 정책 자동 승인) → 감사".
4. **AI는 도구를 쓴다**: AI는 9장 API(sys.* 조회, 쿼리 실행, 파서 시험, 백테스트)를 **요청한 사용자의 권한으로** 호출하고, 답에는 근거 링크를 단다.

### 10-2. include/ai.h 개념(모델 교체 가능)

```c
/* 개념 예시 — 확정 헤더는 include/ 작업에서 정한다 */
struct mzk_ai_provider {              /* 공급자 1개 = 등록 표 한 줄 + 파일 하나 */
    const char *name;                 /* "local-small", "external-api" 등 */
    uint32_t    abi_version;          /* 인터페이스 버전(호환성 검사) */
    uint32_t    caps;                 /* 지원 기능 비트: 생성, 구조화 출력, 도구 호출 */
    int  (*open)(struct mzk_ai_ctx *ctx, const struct mzk_ai_config *cfg);
    int  (*generate)(struct mzk_ai_ctx *ctx, const struct mzk_ai_request *req,
                     struct mzk_ai_response *out);   /* 시간 초과·토큰 상한은 req에 */
    void (*close)(struct mzk_ai_ctx *ctx);
};
```

- **작업(task) 등록 표**: 파서 생성·대시보드 생성·마스킹·쿼리 작성·시나리오·이벤트 해설·소명 지원·장애 진단. 작업마다 `입력 준비 → 공급자 호출 → 검증기 → 적용 제안` 함수 묶음과 **골든셋** 경로를 둔다. 골든셋 정확도가 떨어지면 그 모델·프롬프트 버전은 배포 금지.
- **공급자 2단**: ① 고객 내부에서 도는 전용 소형 모델(공개 가중치 미세조정, 상업 이용 가능 라이선스만) ② 고객이 허용한 외부 API. 같은 인터페이스.
- **외부 전송 통제**: 외부 공급자로 나가는 요청은 마스킹 모듈을 거치고, 원본 로그는 고객 동의 없이 내보내지 않는다. 호출 내역은 감사.

### 10-3. 학습 데이터 수집 구조(A단계부터)

```
원본 로그 → 템플릿 추출(Drain) → 값 제거(IP·사용자·호스트 등을 타입 자리표시자로)
        → 동의 대장 확인(SQLite: 고객·범위·기간·철회) → 내보내기 묶음(서명·버전)
사람이 고친 파서 → 수정 전후 차이(값 제거) → 같은 경로
```

- 실제 값은 외부로 나가지 않는다. 동의가 없으면 묶음을 만들지 않는다. 동의 철회 시 이후 수집 중단·기존 묶음 폐기 기록.
- 이 경로 자체를 A단계에 넣어 둔다(나중에 모으려면 늦음, PLAN 11-1).

## 11. 모듈 구성과 디렉터리 구조(제안)

```
include/                     모듈 사이 인터페이스(공개 헤더만)
  mzk_core.h  mzk_err.h  net.h  batch.h  spool.h  collect.h  parse.h  forward.h
  store.h  index.h  query.h  stream.h  meta.h  ctl.h  ha.h  api.h  sysview.h  ai.h  integ.h
src/
  core/      메모리 예산, 로깅, 시간, 설정 로드, 감독 프로세스
  err/       오류 코드 등록·형식 조립·반복 묶기(sys.errors)
  net/       소켓, TLS, 배치 프레이밍(버전·시퀀스·CRC)
  spool/     디스크 스풀(에이전트·전달 공용)
  agent/     에이전트 진입점, 다중 목적지
  collect/   수집기 유형(등록 표 + 유형별 파일: syslog_udp.c, file_tail.c …)
  parse/     파서(등록 표 + json.c, kv.c, regex.c …), 정규화
  forward/   전달 서버: store-and-forward, 경로 선택
  store/     세그먼트·파티션·manifest, 압축·암호화·해시 체인, 생명주기
  index/     블룸·역인덱스·필드 인덱스
  query/     파서·계획기·실행기, 명령어(등록 표 + 명령어별 파일)
  stream/    스트림 쿼리
  meta/      SQLite 래퍼·마이그레이션·변경 로그
  ctl/       제어 평면, 내장 인증기관, 설정 배포
  ha/        임대·증인·복제
  api/       REST 라우터·명령 등록 표·OpenAPI 생성기
  sysview/   sys.* 공급자 등록과 sys_metrics
  ai/        공급자·작업 등록 표, 템플릿 추출, 동의 대장
  integ/     연동기·액션·웹훅
  cli/       mazkion 명령줄
tests/<module>/              단위 시험 + 퍼징 대상(파서·프레이밍은 필수)
web/                         TypeScript + React 웹 UI(공개 API만 사용)
```

규칙
- 모듈 폴더마다 `README.md`(무엇·왜·확장하는 법)와 `tests/`. 기능 변경은 시험과 함께 커밋.
- **등록 표 패턴**: 확장 지점마다 `registry.c`에 정적 배열 한 줄. 예: 수집기 유형 `{ "syslog_udp", &collector_syslog_udp_ops }`. 등록 표가 있는 확장 지점: 수집기 유형, 파서, 쿼리 명령어, 함수, 기본 대시보드 템플릿, 오류 코드, sys.* 뷰 공급자, API 명령, AI 공급자·작업, 연동기 인증 방식.
- **전역 상태 금지**: 모든 상태는 컨텍스트 구조체(`struct mzk_node_ctx` 등)에 담아 인자로 넘긴다. 예외는 신호 처리 깃발(`volatile sig_atomic_t`) 하나뿐이며, 이것도 모듈 경계 밖으로 노출하지 않는다.
- 함수 60줄·파일 800줄 안팎, 상수·설정 기본값·오류 코드는 각각 한 곳(`mzk_const.h`, 설정 기본값 표, 모듈별 오류 정의 파일).
- 모든 C 소스·헤더·Makefile 첫 줄에 ORIGIN 문구. C는 한 줄마다 한국어 주석. 경고 0(`-Wall -Wextra`, C11) + 보안 컴파일 옵션.

### 12-3. STRIDE 위협과 대응

| 분류 | 위협 예 | 대응 |
|---|---|---|
| 위장(S) | 가짜 에이전트·노드 참여, 탈취한 참여 토큰 재사용 | mTLS·내장 인증기관, 일회용·단기 토큰, 인증서 지문 고정, 같은 ID 동시 접속 경고 |
| 변조(T) | 저장된 로그 수정, 전송 중 변조, 설정 바꿔치기 | 해시 체인·일 단위 서명, 배치 CRC + TLS, 설정 묶음 해시·서명, 패키지 서명 검증 |
| 부인(R) | 관리자가 삭제·정책 변경을 부인 | 해시 체인 감사 로그, 모든 쓰기 API·제어 명령·키 접근 기록 |
| 정보 노출(I) | 디스크 탈취, 화면·뷰에 비밀값 노출, AI·연동기로 원문 유출 | 테이블 암호화, 비밀값은 뷰·API 출력 금지, 마스킹, 동의 없는 외부 전송 금지 |
| 서비스 거부(D) | UDP 폭주, 거대 로그·악성 정규식, 쿼리 폭주, 압축 폭탄 | 상한 있는 큐와 계측된 드롭, 백트래킹 없는 정규식 엔진, 쿼리 메모리·시간·카디널리티 상한, 해제 크기 상한, 테이블별 격리 |
| 권한 상승(E) | 로그 내용이 실행되는 경로(로그 주입·XSS·템플릿 해석), SSRF, 쿼리로 OS 명령 | 로그는 해석·실행하지 않음, 웹은 텍스트로만 표시, 쿼리 언어에 OS 명령 없음, 외부 호출은 등록된 동작만, 프로세스 최소 권한(낮은 포트는 CAP_NET_BIND_SERVICE만, L10) |

추가 규칙: 모든 파서·통신 해석기는 퍼징 통과 필수, 기본 계정·하드코딩 키 금지, SBOM 생성, 의존 라이브러리는 라이선스·취약점 확인 후 `THIRD_PARTY.md` 기록.

## 14. 미결 사항·발주자 승인 필요

### 14-1. 승인 요청

| 번호 | 사항 | 제안 | 대안 |
|---|---|---|---|
| Q1 | 실행 파일 구성 | 서버용 `mazkion` 하나 + 역할 설정, 에이전트는 전용 빌드 | 역할별 정적 실행 파일 4개 |
| Q2 | 역할별 이중화 방식(4장 표 전체) | 수신형 수집 활성-대기+VIP, 주기 수집 임대 기반, 전달 활성-활성, 분석 활성-대기 | 분석 활성-활성(확장과 함께) |
| Q3 | split-brain 방지 | 증인 노드 포함 3표 과반, 증인 없는 2노드는 자동 전환 끔 | 2노드 자동 전환 허용(위험 수용) |
| Q4 | 전달 서버 스풀 손실 | 전달 서버 ACK = 그 서버 디스크 저장. 디스크 영구 손실 시 미전달분 유실 가능을 문서화 | 종단 ACK(분석 저장 후에야 에이전트가 삭제) — 에이전트 디스크 사용 증가 |
| Q5 | 분석 서버 대기 노드의 인덱스 | 측정 후 결정(전송 vs 재생성) | — |
| Q6 | 성능 목표의 "단일 x86 서버" 사양·이벤트 크기 | 시험 서버(16코어·64GB·NVMe 2TB)는 25GbE NIC 없이는 540만 EPS 회선을 감당하지 못함(7-3). 목표 측정용 사양을 따로 정할지 | 실험 서버로 단계별 측정 후 외삽(외삽치는 실측으로 표현 금지) |
| Q7 | UDP 경로의 내구성 | 수신 후 플러시 창(예: 수백 ms [가정]) 안의 데이터는 정전 시 유실 가능, 계수로 표시 | 매 배치 fsync(처리량 저하 측정 필요) |
| Q8 | 블록 내 열 배치 | 행 묶음 + 필드별 열 | 행 단위 + 필드 인덱스만 |
