## 6. 수집·처리 범위 추가 (2026-10-30, 발주자 요청)
모든 유형의 수집 모델과 관련 프로파일, 스트림 쿼리를 구현한다.

| 분류 | 범위 |
|---|---|
| 접속 프로파일 | SSH/SFTP, FTP, DB(계정·접속 문자열), REST API(토큰·OAuth), 클라우드 자격 증명, TLS 인증서. 비밀값은 암호화 저장 |
| 수집 모델: 네트워크 | Syslog UDP/TCP/TLS(RFC 3164·5424), SNMP Trap, NetFlow/sFlow/IPFIX |
| 수집 모델: 파일 | 파일 tail, 디렉터리 감시(패턴·날짜 경로·하위 디렉터리), 로테이션 처리, 멀티라인(로그 시작 정규식), 문자 인코딩 |
| 수집 모델: 원격 파일 | SFTP/FTP 주기 수집(이어받기 위치 기록) |
| 수집 모델: DB | 주기 쿼리 수집(기준 컬럼 증분), PostgreSQL·MySQL/MariaDB 기본, ODBC 경유 Oracle·MSSQL 등 |
| 수집 모델: 시스템 | Windows 이벤트 로그, Linux journald·auditd, 프로세스·성능 지표 |
| 수집 모델: API·메시지 | REST 폴링, Kafka 소비, 클라우드 감사 로그(오브젝트 스토리지 폴링) |
| 파서·정규화 | 정규식·구분자·JSON·키=값 파서, 필드 정규화 규칙, 수집 모델 = 수집 방식 + 파서 + 정규화 묶음 |
| 스트림 쿼리 | 수집 직후 실시간 변환·필터·라우팅·집계 파이프라인, 비동기 실행 옵션, 오류 격리 |
| 행위 프로파일 | 주기 쿼리로 사용자·장비별 기준 행위 학습, 시나리오에서 참조 |

배치: 수집 모델·접속 프로파일·파서는 A·B단계에 기본형, D단계 전까지 전체 유형 완성. 스트림 쿼리는 B단계, 행위 프로파일은 F단계.
예상 영향: 코드 약 2만~3만 줄 추가, 전체 일정 약 1.5~2개월 증가 (총 약 11~14개월).

## 7. 쿼리 언어·매뉴얼·제품 웹사이트 추가 (2026-10-30, 발주자 요청)
| 항목 | 범위 |
|---|---|
| 쿼리 언어 | 기준 제품 쿼리 명령어(FEATURES.md 6장), Splunk SPL, SQL을 공개 문서로 비교 분석해 장점을 합친 자체 언어 설계. 파이프(`검색 \| 명령 \| 명령`) 문법을 기본으로 하고 SQL 문법(`SELECT … FROM 테이블 WHERE …`)도 같은 엔진에서 실행. 문서 문장·예제 복사 금지, 문법은 독자 설계 |
| 쿼리 매뉴얼 | 명령어·함수마다 문법, 인자, 예제, 결과 예시, 관련 명령, 다른 제품 대응 명령(SPL·SQL 대응표)을 실은 상세 매뉴얼. 명령어 정의 한 곳(소스의 명령어 메타데이터)에서 매뉴얼을 자동 생성해 코드와 문서가 어긋나지 않게 함. 이름·분류·키워드·예제 전문 검색 |
| 제품 웹사이트 | 제품 이름 확정 후 제작. 제품 소개, 기능 목록 검색(FEATURES.md 기반), 쿼리 매뉴얼 검색, 설치 안내, 다운로드, 대기자 명단(수익 실험 E2). 상용 SIEM 웹사이트·매뉴얼 구성을 참고하되 문구·디자인 복제 금지. 정적 사이트(TypeScript)로 GitHub Pages 배포 |

배치: 쿼리 언어 설계 문서는 0단계(아키텍처와 함께), 구현은 B단계. 매뉴얼은 B단계부터 명령어가 늘 때마다 자동 갱신. 웹사이트 v0(소개·대기자 명단)는 이름 확정 직후, 기능·매뉴얼 검색은 C단계.

## 10. 저장 보호·백업·오류 기록 요구사항 (2026-10-30, 발주자 요청)

### 10-1. 테이블별 저장 설정
| 기능 | 내용 |
|---|---|
| 암호화 | 테이블마다 저장 암호화 켜기/끄기(AES-256-GCM). 키는 테이블별로 분리하고, 마스터 키로 감싸 보관. 키 교체(rotation) 시 새 데이터는 새 키, 옛 데이터는 백그라운드 재암호화. 키 접근은 감사 기록. 공공 납품용 검증필 암호모듈(KCMVP) 교체 가능 구조 |
| 압축 | 테이블마다 알고리즘·수준 선택(예: 빠른 lz4 / 고압축 zstd 1~19). 압축률·CPU 사용량을 sys.tables에 실시간 표시, 변경 시 다음 파티션부터 적용 |
| 생명주기 | 테이블마다 단계 지정: 뜨거움(빠른 디스크) → 따뜻함(일반 디스크) → 차가움(대용량·고압축) → 보관(외부 저장소) → 삭제. 기간 기준 자동 이동, 법적 보존 잠금(legal hold) 시 삭제 금지, 삭제·이동은 모두 감사 기록 |
| 위변조 방지 | 파티션마다 해시 체인을 남겨 저장 후 변경 여부를 검증(개인정보 접속기록 위변조 방지 의무 대응) |

### 10-3. 내부 오류 기록 — "누가 봐도 무슨 문제인지 아는 로그"
현장 문제: 기존 제품의 내부 오류 로그는 읽어도 무슨 문제인지 모르는 경우가 많다(예외 이름·스택만 남음).
| 원칙 | 내용 |
|---|---|
| 오류 코드 | 모든 오류에 고유 코드(`MZK-<모듈>-<번호>`). 코드마다 매뉴얼 페이지 자동 생성 |
| 사람 말 요약 | 첫 줄은 "무엇이 / 왜 / 어디서"를 한국어(영어 병기)로 한 문장 |
| 영향 | 그래서 무엇이 멈췄거나 늦어지는지(수집 중단, 탐지 공백, 데이터 유실 가능 등) |
| 원인 후보·조치 | 가능성 높은 순서의 원인과 바로 할 조치, 확인용 쿼리 |
| 관련 객체 | 수집기·테이블·노드·사용자의 id와 이름, 추적 ID(같은 사건의 로그를 한 번에 묶음) |
| 기술 상세 | errno·시스템 호출·스택은 따로 접어 두는 칸에(개발자용) |
| 반복 묶기 | 같은 오류는 1건으로 묶고 처음·마지막 발생 시각과 횟수만 증가(로그 폭주 방지) |
| 실시간 검색 | 내부 로그도 MAZKION 자기 테이블(sys.errors)에 저장돼 쿼리·대시보드로 바로 검색 |
| 대시보드 | 오류 현황판(코드별·모듈별·노드별 추이, 새로 생긴 오류, 영향 큰 순서), 누르면 해당 객체 상세로 이동 |

예시:
```
[MZK-COL-0103] 경고 | 수집기 "방화벽-01"(노드 active-01)이 5분째 로그를 받지 못하고 있습니다.
영향: 이 수집기를 쓰는 탐지 시나리오 7개에 입력 공백이 생깁니다.
원인 후보: ① 송신 장비의 시스로그 설정 변경 ② 방화벽에서 UDP 514 차단 ③ 장비 재부팅
조치: 송신 장비에서 전송 대상 확인 → `sys.collectors where name="방화벽-01"`로 마지막 수신 시각 확인
추적 ID: 7f3a… | 처음 17:40:02, 마지막 17:45:02, 6회
```
배치: 오류 기록 형식과 sys.errors는 A단계부터(모든 코드가 처음부터 이 형식으로 오류를 남김), 암호화·압축·생명주기는 B단계, 자동 백업·복원 시험은 G단계, 대시보드는 C단계.

## 11. 자동 온보딩: 원본 로그 → 파서·대시보드·시나리오 자동 생성과 검증 (2026-10-30, 발주자 아이디어)
LLM을 직접 만들지 않는다. 1단은 폐쇄망에서도 도는 결정적 알고리즘(C), 2단은 선택형 보조 AI.

| 단계 | 방법 | 검증 |
|---|---|---|
| ① 형식 판별 | 시스로그(RFC3164/5424), JSON, key=value, CEF/LEEF, CSV, 멀티라인을 자동 판별. 알려진 장비 지문 라이브러리로 제조사·제품 추정 | 판별 신뢰도 표시 |
| ② 템플릿 추출 | 로그 템플릿 마이닝(Drain 계열 알고리즘)으로 같은 모양의 로그를 묶고 변하는 자리(변수)를 찾음 | 묶음별 대표 예시 표시 |
| ③ 필드 타입 추론 | 변수 자리마다 IP·포트·시각·사용자·URL·숫자·해시 등 타입 인식기 적용 | 샘플 전체에서 타입 일관성 % |
| ④ 파서 생성 | 템플릿+타입으로 정규식(백트래킹 없는 엔진 전용) 또는 key=value·JSON 파서를 생성, 표준 필드명으로 정규화 매핑 | **적용률**(파싱 성공 %), 따로 떼어 둔 검증용 샘플 적용률, 필드 누락 %, 처리 속도. 기준 미달이면 사람 확인 요청 |
| ⑤ 대시보드 생성 | 필드 타입에 맞는 기본 위젯(시간별 추이, 상위 출발지·목적지, 차단/허용 비율, 오류율 등)을 자동 배치, 자동 등록 대시보드에 추가 | 빈 위젯·0건 위젯 자동 제거 |
| ⑥ 시나리오 추천 | 로그 종류·필드에 맞는 탐지 규칙을 규칙 라이브러리(공개 Sigma 규칙 등, 라이선스 확인 후)에서 골라 추천 | **과거 데이터 백테스트**(예상 일 알림 수·상위 원인), **합성 공격 로그 주입 시 탐지 여부**, 일정 기간 **그림자 모드**(알림 없이 탐지만 기록) 후 활성화 |
| ⑦ 보조 AI(선택) | 필드의 의미 이름 붙이기, 정규화 매핑 제안, 시나리오 설명 문장 생성. 고객 내부에서 도는 공개 가중치 소형 모델(C/C++ 추론 엔진) 또는 고객이 허용한 외부 API. 모델 라이선스 확인 필수 | AI 제안은 반드시 ④·⑥의 같은 검증을 통과해야 적용. 원본 로그는 고객 동의 없이 외부로 보내지 않음 |

원칙: 자동 생성물은 모두 "제안 → 검증 수치 표시 → 사람 승인(또는 기준 이상 자동 승인 설정)" 순서. 승인 이력은 감사 기록.
배치: ①~④ B·D단계, ⑤ C단계, ⑥ D·F단계, ⑦ F단계 이후 선택 기능.

### 11-1. MAZKION 전용 로그 모델 로드맵 (2026-10-30, 발주자 방향)
목표: 어떤 로그가 들어와도 형식을 판별하고 파서·정규화·대시보드를 만들어 내는 **MAZKION 전용 모델**. 장비별 파서 앱을 사람이 하나하나 유지보수하는 부담을 없앤다.
| 원칙 | 내용 |
|---|---|
| 모델은 "파서를 만드는 데"만 쓴다 | 로그 1건마다 모델을 돌리지 않는다(초당 수십만 건에서 불가능). 새 로그 유형이 나타날 때만 모델이 템플릿·정규식·매핑을 생성하고, 이후엔 C 파서가 처리. 생성 결과는 캐시·재사용(연구 사례: LILAC, FSE 2024 — 템플릿 캐시로 LLM 호출을 수천 분의 1로 줄이고 정확도 향상) |
| 처음부터 만들지 않는다 | 공개 가중치 소형 모델(1B~8B급, 상업 이용 가능한 라이선스만)을 우리 로그 데이터로 미세조정(LoRA). 고객 내부 CPU·소형 GPU에서 추론 |
| 99%는 "검증으로 보장" | 모든 생성 파서는 검증 샘플 적용률·필드 정확도를 측정해 **99% 이상일 때만 자동 적용**, 미달이면 사람 확인 → 그 수정이 다시 학습 데이터가 됨. 자동 적용 범위(커버리지)는 학습이 쌓일수록 넓어짐 |
| 학습 데이터 | ① 공개 로그 데이터셋(Loghub 등, 라이선스 확인) ② 장비 매뉴얼 기반 합성 로그 ③ 고객 동의 시 **값을 지운 템플릿만** 수집(IP·사용자 등 실제 값은 외부로 나가지 않음) ④ 현장에서 사람이 고친 파서 |
| 데이터 수집은 지금부터 설계 | A단계부터 템플릿 추출·익명화·동의 관리 구조를 넣어 둔다(나중에 모으려면 늦음) |
| 측정 기준 | 로그 유형별 그룹 정확도·필드 정확도, 새 유형 자동 적용률, 처리 비용. 매 학습 버전마다 고정 시험셋으로 회귀 시험 |
배치: 데이터 수집 구조 A단계, 결정적 자동 온보딩 B~D단계, 첫 미세조정 모델 F단계(유료 고객 확보 후, 학습 GPU 비용 발생), 이후 지속 개선.
